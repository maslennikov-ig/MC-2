## 1. Что сказал владелец

Issue 63: должностная инструкция «непонятна, для кого она». Нужны три варианта —
HR, руководителю и самому сотруднику. «Сейчас мы всё это смешиваем и ни для кого
не даём полный окончательный вариант».

Issue 64: «блоки генерируются отдельно, мы часто повторяем одну и ту же информацию
в разных блоках… если информация была в предыдущем блоке, в этот блок она не
должна попадать. Как это правильно сделать?»

Решение владельца 2026-08-29 по способу: одна генерация с тремя представлениями
принимается, **если повторов нет внутри каждого представления. Повтор между
представлениями допустим** — их читают разные люди и по отдельности.

## 2. Что измерено 2026-08-29

По 14 завершённым плейбукам (`career_playbooks`, `status='completed'`):

| Блоков                                              | 27                                    |
| Повторяющихся предложений (≥60 знаков)              | 0–1.4%                                |

Два вывода, каждый меняет решение:

**Дублируется смысл, не текст.** Строковая дедупликация не найдёт ничего: 0.8%
общих пятисловок — это шум. Мерить надо пересказ, то есть эмбеддингами.

**Защита от повторов есть и не работает.** `prior-blocks-digest.ts` показывает
блоку, что уже написано; `block_boundaries[block].do_not_repeat` говорит, чего не
касаться; судья считает повтор чужой темы критическим и требует перегенерации
(`career-playbook-prompts.ts:653`). Ломается середина: список «чего не касаться»
сочиняет LLM-спекбилдер, и он то пуст, то содержит все 26 блоков. Запрет либо не
выдан, либо выдан на всё — бесполезен в обоих случаях. При этом канонический
список тем всех 27 блоков уже лежит в коде детерминированно
(`career-playbook-block-topics.ts`).

## 4. Работы

### Фаза 0 — замер до правок

`scripts/measure-playbook-repetition.ts` по 14 завершённым плейбукам, результат в
`docs/`. Без базовой линии никакое «стало лучше» не проверяемо, а жалоба владельца
числа сегодня не имеет.

Измеритель считает: попарную семантическую близость блоков **внутри каждого
представления** и близость абзацев **внутри одного блока** (владелец говорит и про
повторы «в каждом блоке»). Эмбеддинги — Jina, через
`shared/validation/quality-validator.ts` и `shared/jina/`.

### Фаза A — адресат становится свойством блока

1. `packages/shared-types/src/career-playbook-blocks.ts` — поле
   `audiences: readonly CareerPlaybookAudience[]` по таблице §3, минимум один
   адресат у каждого блока.
2. `career-playbook.ts` — тип `CareerPlaybookAudience = 'employee' | 'manager' | 'hr'`.
3. `final-assembler.ts` — `buildRoleGuideView(blocks, audience)`, сборка markdown
   по фильтру. **Схему БД не трогаем**: `generated_blocks` остаётся хранилищем,
   `final_markdown` — полным документом, представления собираются на лету.
4. `career-playbook-prompts.ts` — переменная `block_audiences_md` в промптах групп;
   строку «The reader is an employee doing this job» (:140) заменить на адресность
   по блоку.
5. `PlaybookViewer.tsx` — три вкладки плюс полный документ четвёртой.

### Фаза B — повтор, который можно измерить

6. `do_not_repeat` выводить из канонической карты: темы блоков, с которыми блок
   делит представление и чьи `aliases` не пересекаются с его собственными.
   Перезапись в `spec-builder-canonical.ts`, где спек уже нормализуется на
   канонический макет. Ответ модели по этому полю перестаёт влиять на результат.
7. `prior-blocks-digest.ts` — выжимка не всех предыдущих блоков, а тех, с кем блок
   делит документ.
8. Порог «слишком близко» выбрать по базовой линии фазы 0, хранить в одном месте
   (образец — `retrieval-thresholds.ts`), включить в детерминированный слой рядом
   с `quality-checks.ts` под уже критической категорией `contradiction`. Гейт
   срабатывает только на паре внутри одного представления.

### Фаза C — условная

9. Владелец просит для руководителя часть «как проверять, как отвечать на
   вопросы». Ближайшее сегодня — `block_26`, где руководитель один из трёх
   адресатов. Делать, только если после фазы A видно, что документ руководителя
   беднее двух других; тогда расширять block_26, а не заводить 28-й блок.

## 5. Приёмка

- **AC-1** Каждое из трёх представлений читается как законченный документ.
- **AC-2** Ни один блок не потерян: объединение трёх представлений равно полному
  набору.
- **AC-3** `do_not_repeat` не зависит от ответа модели и содержит только блоки
  того же представления.
- **AC-4** Доля слишком близких пар внутри представления и внутриблочная близость
  абзацев ниже базовой линии фазы 0. Близость **между** представлениями не
  проверяется — это решение владельца, а не упущение.
- **AC-5** `pnpm type-check` и `pnpm test:unit` зелёные.
- **AC-6** Обе задачи закрыты с измерением, не с «выглядит сделанным».

## 6. Границы

- Миграции схемы, reindex, секреты, доступы, force-push — запрещены.
- Каноническую 26-блочную раскладку и темы не менять (`mc2-1slzl`).
- Строковую дедупликацию не делать: измерено, что дублировать нечего.
- Один платный прогон на dev, артефакт читается глазами (`mc2-db696.110`).
  Расход плейбука пишется в `career_playbooks.cost_breakdown` — плейбук **не**
  пишет в `generation_trace`, и запрос по трейсу покажет ноль там, где были сотни
  вызовов.
- `mc2-hpful` (повтор блока внутри урока курса) — другой пайплайн, не входит.
