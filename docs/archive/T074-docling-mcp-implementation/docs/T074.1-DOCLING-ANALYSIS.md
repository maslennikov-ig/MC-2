**Архитектура загрузки файлов (T057 - Complete)**

- Tier-based ограничения:
  - Free: Загрузка запрещена
  - Basic Plus: PDF, TXT, MD (1 файл, 100MB)
  - Standard: + DOCX, HTML, PPTX (3 файла, 1GB)
  - Premium: + изображения PNG/JPG/GIF (10 файлов, 10GB)
- Файлы сохраняются в `/uploads/{organizationId}/{courseId}/{fileId}.{ext}`
- Метаданные в таблице `file_catalog` (PostgreSQL)
- Статус векторизации: `pending`, `indexing`, `indexed`, `failed`

## 2. Обнаруженное решение: Docling

### Что такое Docling?

**GitHub**: https://github.com/docling-project/docling
**Версия**: v2.56.1 (Production/Stable)
**Лицензия**: MIT
**Поддержка**: LF AI & Data Foundation, IBM Research Zurich

**Ключевые возможности**:

- 🗂️ Парсинг множества форматов: PDF, DOCX, PPTX, XLSX, HTML, изображения, аудио
- 📑 **Продвинутое понимание PDF**: page layout, reading order, table structure, code, formulas
- 🧬 Унифицированный формат `DoclingDocument`
- ↪️ Экспорт: Markdown, HTML, DocTags, JSON
- 🔒 **Локальное исполнение** (air-gapped environments)
- 🤖 Интеграции: LangChain, LlamaIndex, Crew AI, Haystack
- 🔍 Обширная OCR поддержка (для сканированных PDF)
- 🎙️ ASR для аудио файлов
- 🔌 **MCP server** для agentic applications

### Технический стек Docling

**Язык**: Python 3.9+
**Зависимости**:

- Pydantic v2 (валидация данных)
- docling-core, docling-parse, docling-ibm-models
- pypdfium2 (PDF парсинг)
- huggingface_hub (ML модели)
- python-docx, python-pptx (Office форматы)
- beautifulsoup4, lxml (HTML)
- pillow (изображения)
- transformers, accelerate (VLM модели)

**Производительность**:

- Поддержка Visual Language Models (GraniteDocling 258M)
- MLX acceleration на Apple Silicon
- Batch processing для больших документов

## 3. Анализ применимости

### ✅ Преимущества для нашего проекта

1. **Полное покрытие форматов**
   - Все наши tier-based форматы поддерживаются:
     - ✅ PDF (с продвинутым пониманием структуры)
     - ✅ DOCX, PPTX, XLSX
     - ✅ HTML
     - ✅ Markdown
     - ✅ Изображения (PNG, JPEG, TIFF)
   - Бонус: поддержка аудио (WAV, MP3) и WebVTT

2. **Продвинутая обработка PDF**
   - Reading order (правильная последовательность текста)
   - Table structure (извлечение таблиц с сохранением структуры)
   - Formula extraction (математические формулы)
   - Code blocks (выделение кода)
   - Image classification (классификация изображений)
   - **Критично для курсов**: сохранение учебной структуры

3. **Унифицированный формат**
   - `DoclingDocument` - единый формат для всех типов документов
   - Упрощает chunking и embedding generation
   - JSON экспорт для хранения в PostgreSQL

4. **Production-ready**
   - LF AI & Data Foundation (промышленный уровень)
   - MIT лицензия (коммерческое использование OK)
   - Активная разработка (v2.56.1, обновления каждую неделю)

5. **Интеграции с нашим стеком**
   - MCP server (может работать как отдельный сервис!)
   - LangChain интеграция (если понадобится в будущем)
   - Локальное исполнение (compliance, GDPR)

### ❌ Недостатки и риски

1. **Языковой барьер: Python vs TypeScript**
   - Наш проект: TypeScript/Node.js
   - Docling: Python 3.9+
   - **Проблема**: Нужна интеграция между двумя runtime

2. **Дополнительная инфраструктура**
   - Требует отдельного Python процесса
   - Управление зависимостями (pip/uv)
   - Deployment complexity (две runtime вместо одной)

3. **Размер зависимостей**
   - Тяжёлые ML библиотеки (transformers, accelerate)
   - Модели Hugging Face (сотни MB)
   - OCR зависимости (если включить)
   - **Impact**: Docker image размер, startup time

4. **Производительность IPC**
   - Inter-process communication overhead
   - Serialization/deserialization
   - Potential bottleneck для batch processing

5. **Maintenance burden**
   - Два языка в проекте (TypeScript + Python)
   - Два набора тестов
   - Два набора CI/CD пайплайнов

## 4. Варианты интеграции

### Вариант A: Docling MCP Server 🌟 РЕКОМЕНДУЕМЫЙ

**Описание**: Использовать официальный Docling MCP server как отдельный микросервис

**Архитектура**:

```
TypeScript API (tRPC)
    ↓ (HTTP/MCP protocol)
Docling MCP Server (Python)
    ↓ (parsed documents)
TypeScript API → Chunking → Jina → Qdrant
```

**Плюсы**:

- ✅ Официальная поддержка (часть Docling project)
- ✅ MCP protocol (стандартизированный интерфейс)
- ✅ Лёгкая замена (можно переключиться на другой парсер)
- ✅ Независимый scaling (можно масштабировать отдельно)
- ✅ Изоляция сбоев (падение Python не роняет Node.js)
- ✅ Можем использовать другие MCP servers в будущем

**Минусы**:

- ❌ Дополнительный сервис (deployment complexity)
- ❌ Network latency (хотя минимальный для локального)
- ❌ Требует MCP client в TypeScript (есть готовые решения)

**Усилия**: 2-3 дня

- День 1: Setup Docling MCP server, конфигурация
- День 2: TypeScript MCP client, интеграция
- День 3: Тестирование, документация

**Технический стек**:

- Docling MCP Server (Python, официальный)
- @modelcontextprotocol/sdk (TypeScript MCP client)
- Docker для deployment
- Environment variables для конфигурации

---

### Вариант B: Python Microservice (REST API)

**Описание**: Создать отдельный Python микросервис с REST API

**Архитектура**:

```
TypeScript API (tRPC)
    ↓ (HTTP REST)
Python Service (FastAPI)
    ↓ (uses Docling)
Returns: parsed JSON
    ↓
TypeScript API → Chunking → Jina → Qdrant
```

**Плюсы**:

- ✅ Простой HTTP REST (знакомый протокол)
- ✅ Полный контроль над API
- ✅ Можем добавить кэширование, rate limiting
- ✅ Swagger/OpenAPI документация

**Минусы**:

- ❌ Нужно писать REST API с нуля
- ❌ Больше кода (endpoints, validation, error handling)
- ❌ Не используем готовое решение (MCP)
- ❌ Дублирование функциональности (MCP server уже есть)

**Усилия**: 4-5 дней

- День 1-2: FastAPI setup, Docling интеграция
- День 3: Endpoints для каждого формата
- День 4: Error handling, rate limiting
- День 5: Тестирование, документация

**Технический стек**:

- FastAPI (Python web framework)
- Pydantic (валидация)
- Docling library
- uvicorn (ASGI server)

---

### Вариант C: Child Process (Node.js)

**Описание**: Запускать Docling CLI как child process из Node.js

**Архитектура**:

```
TypeScript API
    ↓ (spawn/exec)
Python CLI (docling)
    ↓ (stdout/file)
Parse output in TypeScript → Chunking → Jina → Qdrant
```

**Плюсы**:

- ✅ Простая интеграция (child_process.spawn)
- ✅ Не требует отдельного сервиса
- ✅ Использует официальный CLI

**Минусы**:

- ❌ Process spawning overhead (каждый раз)
- ❌ Parsing stdout (хрупкий)
- ❌ Сложно обрабатывать ошибки
- ❌ Не scale-friendly (блокирует event loop)
- ❌ Python startup время на каждый запрос

**Усилия**: 2 дня

- День 1: Child process wrapper, stdout parsing
- День 2: Error handling, тестирование

**Не рекомендуется** для production (performance issues)

---

### Вариант D: TypeScript альтернативы

**Описание**: Найти/использовать TypeScript библиотеки вместо Docling

**Существующие решения**:

- `pdf-parse` (PDF → text, basic)
- `mammoth` (DOCX → HTML)
- `pdf-lib` (PDF manipulation)
- `pdfjs-dist` (Mozilla PDF.js)
- `tesseract.js` (OCR)

**Плюсы**:

- ✅ Нативный TypeScript (нет IPC overhead)
- ✅ Единый runtime (Node.js)
- ✅ Проще deployment

**Минусы**:

- ❌ **Нет продвинутого понимания структуры PDF**
- ❌ Нужно комбинировать несколько библиотек
- ❌ Качество парсинга хуже, чем Docling
- ❌ Нет таблиц, формул, reading order
- ❌ Больше maintenance (кастомный код)

**Сравнение качества**:
| Feature | Docling | TypeScript libs |
|---------|---------|-----------------|
| PDF layout | ✅ Advanced | ❌ Basic text extraction |
| Tables | ✅ Structure preserved | ❌ Text only |
| Formulas | ✅ LaTeX | ❌ Not supported |
| Reading order | ✅ Correct | ❌ Random |
| DOCX | ✅ Full structure | ⚠️ HTML only |
| Images in docs | ✅ Classified | ❌ Ignored |

**Усилия**: 5-7 дней

- День 1-2: Исследование библиотек
- День 3-4: Интеграция множества библиотек
- День 5-6: Тестирование на реальных документах
- День 7: Bugfixes, edge cases

**Не рекомендуется**: качество парсинга критично для курсов

## 7. Риски и митигация

### Риск 1: MCP Protocol не подходит

**Вероятность**: Низкая (10%)
**Impact**: Высокий
**Митигация**:

- Fallback на Вариант B (REST API)
- MCP protocol стабильный (Anthropic backed)
- Есть production примеры использования

### Риск 2: Performance проблемы

**Вероятность**: Средняя (30%)
**Impact**: Средний
**Митигация**:

- Async processing via BullMQ (уже есть)
- Batch processing для multiple files
- Caching parsed results
- Rate limiting на uploads

### Риск 3: Python зависимости конфликты

**Вероятность**: Низкая (15%)
**Impact**: Средний
**Митигация**:

- Docker изоляция (полностью изолированная environment)
- `uv` package manager (быстрый, надёжный)
- Pin versions в requirements.txt

### Риск 4: Большой размер Docker image

**Вероятность**: Высокая (70%)
**Impact**: Низкий
**Митигация**:

- Multi-stage Docker build
- Использовать slim Python images
- Убрать dev dependencies в production
- Ожидаемый размер: ~2-3GB (приемлемо)
