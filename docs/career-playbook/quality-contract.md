# Career Playbook — контракт качества (v1)

Нормативный документ. Задаёт правила, которым обязан удовлетворять сгенерированный Role Guide, и
механизмы, которые эти правила обеспечивают. Реализация обязана следовать этому контракту; при
расхождении кода и контракта исправляется код либо контракт правится осознанно и с записью в
Beads.

Причины появления контракта: [quality-root-cause-2026-08-11.md](./quality-root-cause-2026-08-11.md).
План работ: [../plans/buzzing-jingling-oasis.md](../plans/buzzing-jingling-oasis.md).

## Принципы

1. **Числа приходят из одного места.** Любое повторяемое числовое обязательство существует ровно в
   одной записи реестра метрик и цитируется блоками дословно.
2. **Точная внешняя статистика требует источника.** Нет источника — нет точного числа.
   Формулировка переписывается в явную гипотезу.
3. **Профилактика дешевле лечения.** Блок должен получать контекст, достаточный, чтобы не создать
   противоречие, а не только проверяться постфактум.
4. **Детерминированное лучше вероятностного.** Всё, что формализуется регулярным выражением и
   сравнением с реестром, проверяется кодом: это бесплатно, мгновенно и не зависит от того, какая
   модель досталась судье.
5. **Стилистика не ведёт к регенерации.** Тон, «слишком обобщённо», «звучит как HR-жаргон» — это
   максимум предупреждение. Правило сохраняется из текущей реализации, оно верное.

## 1. Реестр метрик (`metric_ledger`)

### Схема

Расширение `CareerPlaybookRoleProfileSpecSchema` в
`packages/shared-types/src/career-playbook.ts`:

```ts
export const CareerPlaybookMetricLedgerEntrySchema = z.object({
  key: z.string().min(1), // стабильный snake_case id: 'pipeline_coverage'
  label: z.string().min(1), // как метрика называется в тексте документа
  unit: z.string(), // 'x' | '%' | 'дней' | 'шт' | ''
  target: z.string().min(1), // '>=3x'
  green: z.string(), // '>=3x'
  yellow: z.string(), // '2-2.9x'
  red: z.string(), // '<2x'
  review_period: z.string(), // 'неделя' | 'месяц' | 'квартал' | 'год'
  provenance: z.enum(['company_source', 'user_answer', 'benchmark', 'assumption']),
  source_ref: z.string().nullable(), // id записи evidence_ledger либо null
});
```

### Правила заполнения

- Реестр строит LLM в spec-builder, затем код **детерминированно нормализует**: схлопывает
  дубликаты по `key`, отбрасывает записи с пустым `target`, приводит `unit` к нижнему регистру.
  Паттерн уже применён для канонической раскладки блоков —
  `normalizeRoleProfileSpecToCanonicalBlockTopics`
  (`stages/stage-career-playbook/nodes/spec-builder-canonical.ts`). Переиспользовать его форму,
  а не изобретать новую.
- Минимум записей — по числу `focus_areas.primary_kpis`. Каждая метрика из `primary_kpis` обязана
  иметь запись в реестре.
- `provenance` определяет допустимую формулировку в тексте:

| `provenance`     | Откуда                                | Как подаётся в документе                       |
| ---------------- | ------------------------------------- | ---------------------------------------------- |
| `company_source` | Загруженный корпус компании           | Как факт                                       |
| `user_answer`    | Ответ в мастере                       | Как факт                                       |
| `benchmark`      | Внешний источник из `evidence_ledger` | Как ориентир со ссылкой `[Sn]`                 |
| `assumption`     | Ничем не подтверждено                 | Как гипотеза с пометкой «требует согласования» |

### Правило для блоков

> Любое число, присутствующее в `metric_ledger`, воспроизводится дословно вместе с порогами
> светофора. Вводить новое числовое значение для метрики, которая есть в реестре, запрещено.
> Метрика, которой нет в реестре, вводится качественно, без точного порога.

## 2. Реестр источников (`evidence_ledger`)

### Схема

```ts
export const CareerPlaybookEvidenceEntrySchema = z.object({
  id: z.string().min(1), // 'S1', 'S2', ... — присваивается кодом
  url: z.string().min(1),
  title: z.string().min(1),
  claim: z.string().min(1), // конкретное утверждение, которое источник подтверждает
  retrieved_at: z.string().min(1),
});
```

### Правило заполнения

`evidence_ledger` **заполняется кодом**, а не моделью: собирается прямо из результата
`runCareerPlaybookWebResearch` в `spec-builder.ts` после парсинга спеки. Идентификаторы `S1..Sn`
присваиваются детерминированно по порядку. Модели запрещено выдумывать записи реестра: любые
`evidence_ledger` из ответа LLM отбрасываются и перезаписываются.

Причина: в прогоне 2026-08-11 URL существовали только внутри промпта spec-builder и терялись, а
модель произвольно сочиняла обороты «Research shows» без какой-либо привязки
(см. RC-4 в карте причин).

### Правило для блоков

> Точная статистика о рынке, отрасли, конкурентах или влиянии ИИ допускается только со ссылкой
> `[Sn]` на запись `evidence_ledger`. Если подходящей записи нет — утверждение переписывается без
> точного числа, как явная гипотеза («ориентир, требует проверки на ваших данных»).

Раздел «Источники» с раскрытием `[Sn] → title, url` добавляется в блок 25.

### Режим без источников

Пустой или отсутствующий `TAVILY_API_KEY` перестаёт быть тихим: пишется предупреждение в
`quality_issues` playbook-а, генерация переходит в режим «без внешней статистики», и
`validateUnsourcedStatistics` режет любое точное внешнее число.

## 3. Дата генерации (`generated_on`)

- Поле `generated_on: z.string().min(1)` в `RoleProfileSpec`, заполняется кодом из системного
  времени в момент построения спеки.
- Передаётся отдельной переменной во все групповые промпты, промпт судьи и промпт регенератора.

### Правило для блоков

> В планах, графиках и расписаниях используются только относительные обозначения: «День 1-30»,
> «Неделя 2», «Квартал 1», «Месяц 3». Абсолютный календарный год допускается только в футере
> блока 25 и только равным `generated_on`.

## 4. Маркировка примеров

Продуктовое решение: конкретные примеры остаются — они делают документ полезным «из коробки», — но
обязаны быть однозначно отличимы от корпоративной правды.

### Правило для блоков

> Company-specific значение, не подтверждённое загруженным корпусом или ответом пользователя
> (оклад, бонус, ARR, бюджет, имя человека, название внутреннего инструмента), остаётся
> конкретным, но обязано нести единый маркер: `(пример — заменить)` для русского,
> `(example — replace)` для английского. Маркер ставится сразу после значения, в той же строке или
> ячейке таблицы.

Все помеченные значения дополнительно перечисляются в чеклисте внедрения (блок 26) как позиции для
калибровки перед публикацией.

Формулировка «use a realistic invented example and mark it as an example» из текущих промптов
заменяется на это правило с явным форматом маркера. Существующий запрет на сырые плейсхолдеры
(`[Name]`, `{value}`) сохраняется без изменений.

## 5. Контекст предыдущих блоков (`prior_blocks_digest`)

Строится детерминированно из `state.generatedBlocks` перед вызовом каждого группового генератора
и содержит:

- анти-цели из блока 2 (полный список);
- все числовые обязательства, уже произнесённые в принятых блоках, в формате `метрика: значение`;
- названные роли, инструменты и лица;
- обещанные ритмы взаимодействия (ежедневно / еженедельно / ежемесячно).

Ограничение по размеру: не более 1500 токенов; при превышении усечение по приоритету — анти-цели
и числовые обязательства сохраняются всегда.

Причина: сейчас группа 2 физически не может свериться с анти-целями группы 1, потому что в промпт
передаются только `spec_json`, `content_language` и заголовки (RC-2).

## 6. Детерминированные проверки

Добавляются в `stages/stage-career-playbook/nodes/cross-block-judge-checks.ts` рядом с
существующими `validateAntiGoalsMinimum` / `validateDecisionMatrixMinimum` /
`validateFailureModesMinimum` и подключаются в `runCareerPlaybookDeterministicChecks`
(`nodes/cross-block-judge.ts:261-292`).

| Проверка                          | Логика                                                                                                                                                                                             | Категория          | Что ловит из прогона                                    |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ | ------------------------------------------------------- |
| `validateMetricLedgerConsistency` | Для каждой записи реестра ищет `label` (и известные синонимы) в тексте блока; извлекает число рядом; сравнивает с `target`/`green`/`yellow`/`red`. Расхождение → `critical`                        | `metric_conflict`  | 2× против 3×, ±10% против ±5%, 85/90/100%, 15/10/25/30% |
| `validateUnsourcedStatistics`     | Точный процент или множитель в одном предложении с маркером внешнего утверждения (`research`, `studies`, `benchmark`, `industry`, `market`, `по данным`, `исследования`) и без `[Sn]` → `critical` | `unsourced_claim`  | «90-95% точность», «28% отклик», «95% еженедельно»      |
| `validateExampleMarking`          | Денежная сумма, именованное лицо или внутренний инструмент при `business_context.mode === 'universal'` без маркера примера → `critical`                                                            | `unmarked_example` | $120,000/$60,000, $50M ARR                              |
| `validateRelativeDates`           | Абсолютный год, не равный году `generated_on`, вне блока 25 → `critical`                                                                                                                           | `stale_date`       | Gantt «январь-март 2025»                                |
| `validateAntiGoalConflict`        | Ежедневная обязанность «на каждого подчинённого» при анти-цели о микроменеджменте в `prior_blocks_digest` → `critical`                                                                             | `contradiction`    | Находка №3 ревью                                        |

Требования к реализации проверок:

- Каждая проверка — чистая функция без сетевых вызовов, покрытая юнит-тестами на позитивном и
  негативном примере из реального прогона (`artifacts/career-playbook-quality/career-playbook.md`).
- Ложное срабатывание дороже пропуска только для `validateExampleMarking`: там допускается
  консервативный список паттернов, чтобы не помечать бенчмарки со ссылкой.
- Проверки не смотрят внутрь fenced-блоков Mermaid и кода.

`CareerPlaybookJudgeIssueCategorySchema` и `isCareerPlaybookJudgeCriticalCategory`
(`packages/shared-types/src/career-playbook.ts`) расширяются.

**Критичные категории (ведут к регенерации):**

| Категория                | Статус        | Определение                                                                                                              |
| ------------------------ | ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `contradiction`          | **расширена** | Блок противоречит RoleProfileSpec, **или противоречит другому блоку**, или повторяет тему, закреплённую за другим блоком |
| `format_minimum`         | без изменений | Не выполнен жёсткий формат-минимум                                                                                       |
| `wrong_language`         | без изменений | Пользовательский текст не на целевом языке                                                                               |
| `unresolved_placeholder` | без изменений | Остались сырые плейсхолдеры                                                                                              |
| `invented_number`        | без изменений | Company-specific число заявлено как факт без подтверждения                                                               |
| `metric_conflict`        | **новая**     | Значение метрики расходится с `metric_ledger`                                                                            |
| `unsourced_claim`        | **новая**     | Точная внешняя статистика без ссылки на `evidence_ledger`                                                                |
| `stale_date`             | **новая**     | Абсолютная дата вне года `generated_on`                                                                                  |
| `unmarked_example`       | **новая**     | Company-specific пример в universal-режиме без маркера                                                                   |

**Некритичные:** `style` и любая категория, которую модель не проставила. Правило «`style` никогда
не ведёт к регенерации» сохраняется вместе с защитным понижением
`downgradeNonTaxonomyCriticalIssues`.

Расширение `contradiction` возвращает требование, которое было в исходной спецификации
(`../plans/career-playbook/03-prompts-structure.md:281` — «anti-goals из блока 2 не противоречат
duties из блока 4») и потерялось при переписывании таксономии.

## 8. Редакторские правила

### 8.1 Рубрика решений (блок 5)

Одна метка «one-way / two-way door» заменяется четырьмя независимыми осями:

| Ось                       | Значения                                                       |
| ------------------------- | -------------------------------------------------------------- |
| Обратимость               | обратимо / обратимо с издержками / необратимо                  |
| Радиус поражения          | команда / функция / компания / клиент                          |
| Контрактные обязательства | нет / есть срок / есть штраф                                   |
| Уровень согласования      | самостоятельно / уведомить / согласовать / решает руководитель |

Смена стадий CRM и выбор вендора классифицируются как «обратимо с издержками», а не как
необратимые. Найм и увольнение остаются высококонсеквентными.

### 8.2 Карьерная лестница (блок 11)

- Следующий уровень не может совпадать по смыслу с текущим: «CRO → Chief Revenue Officer /
  President of Revenue» запрещено.
- «Senior <роль> (IC)» запрещено для роли с подчинёнными, если по контексту это управленческая
  позиция.
- Каждый переход несёт критерий продвижения и срок в относительных единицах.

### 8.3 Точность формулировок метрик

Точность прогноза описывается через абсолютную ошибку, а не через «точность > ±20%». Формулировка
вида «accuracy consistently >±20%» смешивает точность с отклонением и запрещена.

## 9. Бюджет генерации

| Параметр           | Текущее (прогон 2026-08-11) |         Цель |
| ------------------ | --------------------------: | -----------: |
| Стоимость          |                     $0.1226 |  ≤ **$0.35** |
| Время              |                      56 мин | ≤ **25 мин** |
| Регенераций блоков |                          13 |          ≤ 6 |

Как достигается — см. раздел «Надёжность и бюджет» в
[плане работ](../plans/buzzing-jingling-oasis.md). Ключевое: устранение обрезки spec-builder
(19 минут) и снижение `timeout_ms` с 300 000 до 120 000.

Чек стоимости обязан фиксировать **неуспешные и оборванные по таймауту** попытки со стоимостью
`unknown`. Сейчас их в `costBreakdown` нет вообще, и приложение не может ни подтвердить, ни
опровергнуть, что провайдер выставит счёт за прерванные вызовы.

## 10. Пороги приёмки

Полная процедура — в [плане приёмки](../plans/career-playbook/06-quality-acceptance.md).
Кратко:

| Измерение                         | База 2026-08-11 |     Порог |
| --------------------------------- | --------------: | --------: |
| Полнота                           |           5 / 5 |       ≥ 5 |
| Согласованность                   |           2 / 5 |       ≥ 4 |
| Практическая польза               |           3 / 5 |       ≥ 4 |
| Обоснованность и прослеживаемость |           1 / 5 |       ≥ 3 |
| Решения и управление рисками      |           3 / 5 |       ≥ 4 |
| Качество PDF                      |           2 / 5 |       ≥ 4 |
| Обложка                           |           3 / 5 |       ≥ 3 |
| **Общая**                         |     **2.6 / 5** | **≥ 4.0** |

Жёсткие условия, не сводимые к баллам:

- Ноль критичных находок по пяти детерминированным проверкам.
- Ноль полностью пустых страниц в PDF и ноль фрагментов сырого Markdown.
- Ноль абсолютных календарных дат вне футера.
- Стоимость и время в пределах раздела 9.
