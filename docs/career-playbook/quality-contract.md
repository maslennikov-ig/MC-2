# Career Playbook — контракт качества (v1)

Нормативный документ. Задаёт правила, которым обязан удовлетворять сгенерированный Role Guide, и
механизмы, которые эти правила обеспечивают. Реализация обязана следовать этому контракту; при
расхождении кода и контракта исправляется код либо контракт правится осознанно и с записью в
Beads.

Причины появления контракта: [quality-root-cause-2026-08-11.md](./quality-root-cause-2026-08-11.md).
План работ: [../plans/buzzing-jingling-oasis.md](../plans/buzzing-jingling-oasis.md).

## Принципы

1. **Числа приходят из одного места.** Любое повторяемое числовое обязательство существует ровно в
   одной записи реестра метрик и цитируется блоками дословно.
2. **Точная внешняя статистика требует источника.** Нет источника — нет точного числа.
   Формулировка переписывается в явную гипотезу.
3. **Профилактика дешевле лечения.** Блок должен получать контекст, достаточный, чтобы не создать
   противоречие, а не только проверяться постфактум.
4. **Детерминированное лучше вероятностного.** Всё, что формализуется регулярным выражением и
   сравнением с реестром, проверяется кодом: это бесплатно, мгновенно и не зависит от того, какая
   модель досталась судье.
5. **Стилистика не ведёт к регенерации.** Тон, «слишком обобщённо», «звучит как HR-жаргон» — это
   максимум предупреждение. Правило сохраняется из текущей реализации, оно верное.
6. **Повтор определяется внутри документа для одного читателя.** Пара блоков сравнивается, только
   если оба входят хотя бы в одно общее представление: сотруднику, руководителю или HR. Повтор
   между представлениями допустим, потому что эти документы читают разные люди по отдельности.

## 1. Реестр метрик (`metric_ledger`)

### Схема

Расширение `CareerPlaybookRoleProfileSpecSchema` в
`packages/shared-types/src/career-playbook.ts`:

```ts
export const CareerPlaybookMetricLedgerEntrySchema = z.object({
  key: z.string().min(1), // стабильный snake_case id: 'pipeline_coverage'
  label: z.string().min(1), // как метрика называется в тексте документа
  unit: z.string(), // 'x' | '%' | 'дней' | 'шт' | ''
  target: z.string().min(1), // '>=3x'
  green: z.string(), // '>=3x'
  yellow: z.string(), // '2-2.9x'
  red: z.string(), // '<2x'
  review_period: z.string(), // 'неделя' | 'месяц' | 'квартал' | 'год'
  provenance: z.enum(['company_source', 'user_answer', 'benchmark', 'assumption']),
  source_ref: z.string().nullable(), // id записи evidence_ledger либо null
});
```

### Правила заполнения

- Реестр строит LLM в spec-builder, затем код **детерминированно нормализует**: схлопывает
  дубликаты по `key`, отбрасывает записи с пустым `target`, приводит `unit` к нижнему регистру.
  Паттерн уже применён для канонической раскладки блоков —
  `normalizeRoleProfileSpecToCanonicalBlockTopics`
  (`stages/stage-career-playbook/nodes/spec-builder-canonical.ts`). Переиспользовать его форму,
  а не изобретать новую.
- Минимум записей — по числу `focus_areas.primary_kpis`. Каждая метрика из `primary_kpis` обязана
  иметь запись в реестре.
- `provenance` определяет допустимую формулировку в тексте:

| `provenance`     | Откуда                                | Как подаётся в документе                       |
| ---------------- | ------------------------------------- | ---------------------------------------------- |
| `company_source` | Загруженный корпус компании           | Как факт                                       |
| `user_answer`    | Ответ в мастере                       | Как факт                                       |
| `benchmark`      | Внешний источник из `evidence_ledger` | Как ориентир со ссылкой `[Sn]`                 |
| `assumption`     | Ничем не подтверждено                 | Как гипотеза с пометкой «требует согласования» |

### Правило для блоков

> Любое число, присутствующее в `metric_ledger`, воспроизводится дословно вместе с порогами
> светофора. Вводить новое числовое значение для метрики, которая есть в реестре, запрещено.
> Метрика, которой нет в реестре, вводится качественно, без точного порога.

## 1bis. Реестр ритмов (`cadence_ledger`)

Добавлен 2026-08-30 после разбора прогона `d5137bc5`. Числа имели канонического владельца и
не спорили — по числам был ровно один дефект. Ритмы владельца не имели, и каждый блок объявлял
свой: обзор воронки шёл **еженедельно** в блоках 3, 4, 21, 22, 23, 26 и **ежеквартально** в блоках
4, 13, 14, 15, 16. Одно расхождение дало пять претензий судьи, и ни одну из них нельзя было
починить регенерацией одного блока: перепишешь block_26 под «ежеквартально» — разойдётся block_3.
Цикл не сходился и выжигал потолок в 30 регенераций.

### Схема

```ts
export const CareerPlaybookCadenceLedgerEntrySchema = z.object({
  key: z.string().min(1), // стабильный snake_case id: 'pipeline_review'
  label: z.string().min(1), // как обязательство называется в тексте документа
  cadence: z.string().min(1), // нормализуется в один из шести токенов
  owner: z.string(), // кто ведёт
  scope: z.string(), // 'на каждого подчинённого' | 'вся команда'
});
```

### Правила заполнения

- Реестр строит LLM в spec-builder, затем код **детерминированно нормализует** —
  `normalizeCareerPlaybookCadenceLedger` в `nodes/quality-ledger.ts`. Та же форма, что у реестра
  метрик: схлопывает дубликаты по `key` (побеждает первая запись), приводит `cadence` к словарю.
- Словарь ровно один и один на всех: `CAREER_PLAYBOOK_CADENCE_WORDS` — `daily`, `weekly`,
  `biweekly`, `monthly`, `quarterly`, `annual`. По нему же `quality-checks.ts` распознаёт ритм в
  тексте блока. Вторая копия словаря позволила бы реестру принять слово, которого проверка не
  видит, — а это ровно то, как ритм ускользает от сравнения.
- Запись, чей ритм не приводится к словарю, **отбрасывается**. Обоснование то же, что у метрики
  без `target`: строка, которую нельзя процитировать, ничего не ограничивает, но позволяет блоку
  «сослаться на реестр», выбрав ритм самостоятельно.

### Правило для блоков

> Периодичность любого обязательства, присутствующего в `cadence_ledger`, воспроизводится
> дословно. Обязательство, которого в реестре нет, всё равно имеет **один** ритм на весь документ:
> тот, что уже опубликован в дайджесте, а если не опубликован — тот, что блок выбирает здесь.

### Правило для проверки

`validateCadenceConsistency` отвечает на вопрос «какой блок неправ», а не «эти блоки спорят».
Канон берётся из реестра; если записи нет — у блока, который публикует ритм **первым** по
`position` из каталога. Претензия заводится на **каждый** отклонившийся блок отдельно и называет
нужный ритм. Так межблочное противоречие становится починимым одной регенерацией на блок.

Предыдущая реализация сортировала id блоков как строки и называла `block_4` «более поздним», чем
`block_15`, то есть отправляла на переписывание блок, который был прав.

## 1ter. Реестр сроков (`milestone_ledger`)

Добавлен 2026-08-31 после разбора прогона `2896e72f`. Числа получили владельца, ритмы получили
владельца, а сроки остались личным мнением каждого блока. Role Canvas (блок 24) обещал первый
прогноз «к неделе 4», тогда как план онбординга (блок 14) ставил его на неделю 2; блок 26 требовал
двух кварталов обучения против блока 23, которому хватает одной сопровождённой передачи. Ни то, ни
другое недостижимо для проверки чисел или ритмов: срок наступления — это ни то, ни другое.

### Схема

```ts
export const CareerPlaybookMilestoneLedgerEntrySchema = z.object({
  key: z.string().min(1), // стабильный snake_case id: 'first_forecast'
  label: z.string().min(1), // как обязательство называется в тексте документа
  offset: z.string().min(1), // нормализуется в «unit N»: day 30, week 2, month 1, quarter 2
  owner: z.string(), // кто отвечает
  scope: z.string(), // на кого распространяется
});
```

### Правила заполнения

- Реестр строит LLM в spec-builder, затем код нормализует — `normalizeCareerPlaybookMilestoneLedger`
  в `nodes/quality-ledger.ts`. Та же форма, что у двух других реестров.
- Единица сравнения — **дни**: `day N` → N, `week N` → N×7, `month N` → N×30, `quarter N` → N×90.
  Гайд законно смешивает единицы для одного обязательства («Day 60» и «первые два месяца» — одно и
  то же обещание), и только общая единица позволяет это утверждать.
- Словарь `CAREER_PLAYBOOK_MILESTONE_UNITS` один на всех, как и у ритмов: по нему же
  `milestone-checks.ts` распознаёт срок в тексте блока.
- Запись, чей срок не читается, отбрасывается — по той же причине, что и ритм вне словаря.

### Правило для блоков

> Срок любого ramp-обязательства из `milestone_ledger` воспроизводится дословно, на языке гайда.
> Блок-сводка (Role Canvas, чек-лист внедрения) **пересказывает** эти даты, а не назначает их.
> FAQ (блок 18) их вообще не печатает: он отвечает на вопрос и отправляет читателя за датой в блок 14.

### Правило для проверки

`validateMilestoneConsistency` (`nodes/milestone-checks.ts`) находит строку реестра в тексте по
словам её же `label`, берёт ближайший временной токен **внутри того же элемента перечисления** и
сравнивает в днях. Претензия заводится на отклонившийся блок и называет канонический срок.

`validateRampOwnership` (там же) — дополнение к ней: она срабатывает ровно на том, что первая
пропускает, — на дате, которая **совпадает** с реестром. Совпадение и есть проблема: реестр появился
потому, что факт, пересказанный в двух местах, расходится, и любой пересказ верен ровно до того
прогона, где он перестаёт быть верным.

Претензия **не называет блок-владельца**, и первая редакция, которая называла, была неправа. Она
ранжировала кандидатов так же, как проверка ритмов, — побеждает тот, кто утверждает чаще, — и на
прогоне b7925b1d выбрала block_4 (обязанности) вместо block_14, который публикует весь ramp. Причина
не в настройке: матчер читает в block_4 пять обязательств, а в block_14 — одно из восьми, потому что
block_14 публикует ramp нумерованным списком и тремя таблицами спринтов, которые это семейство
проверок читает плохо (mc2-nedcb). Средство, называющее авторитет, обязано быть в нём уверено; здесь
это не нужно — лекарство состоит в удалении дат, а не в их переносе.

Единственное, что проверка всё ещё спрашивает у документа: не единственный ли блок 18 несёт ramp.
Если единственный — эти даты и есть единственное место, где читатель их получает, и удаление теряет
факт, а не копию.

Область — только блок 18, и это замер, а не предпочтение. По двум сохранённым прогонам: «любой блок,
кроме владельца» даёт 4 и 6 блоков (22, 24 и 26 пересказывают по замыслу — см. правило выше), «блок,
который ссылается на владельца и всё равно копирует» — 4 и 3, а «только FAQ» — ровно по одному, тому
самому. Прогон 4e355bf4 пересказал в блоке 18 весь ramp одной строкой; b7925b1d, уже получив в
промпте указание ссылаться, открыл блок словами «даты — в блоке 14» и следующим же ответом напечатал
Week 2, Day 30 и Day 60.

Консенсусного fallback здесь **нет**, в отличие от ритмов. У ритмов шесть канонических слов, и
«большинство блоков говорит weekly» — настоящий замер; сроки — открытые числа в четырёх единицах, и
голосование среди нестрого сопоставленных фраз изобретало бы конфликты в блоках, которые правы. Без
строки реестра проверка молчит — и точно так же она молчит на всех гайдах, сгенерированных до
2026-08-31.

## 2. Реестр источников (`evidence_ledger`)

### Схема

```ts
export const CareerPlaybookEvidenceEntrySchema = z.object({
  id: z.string().min(1), // 'S1', 'S2', ... — присваивается кодом
  url: z.string().min(1),
  title: z.string().min(1),
  claim: z.string().min(1), // конкретное утверждение, которое источник подтверждает
  retrieved_at: z.string().min(1),
});
```

### Правило заполнения

`evidence_ledger` **заполняется кодом**, а не моделью: собирается прямо из результата
`runCareerPlaybookWebResearch` в `spec-builder.ts` после парсинга спеки. Идентификаторы `S1..Sn`
присваиваются детерминированно по порядку. Модели запрещено выдумывать записи реестра: любые
`evidence_ledger` из ответа LLM отбрасываются и перезаписываются.

Причина: в прогоне 2026-08-11 URL существовали только внутри промпта spec-builder и терялись, а
модель произвольно сочиняла обороты «Research shows» без какой-либо привязки
(см. RC-4 в карте причин).

### Правило для блоков

> Точная статистика о рынке, отрасли, конкурентах или влиянии ИИ допускается только со ссылкой
> `[Sn]` на запись `evidence_ledger`. Если подходящей записи нет — утверждение переписывается без
> точного числа, как явная гипотеза («ориентир, требует проверки на ваших данных»).

Раздел «Источники» с раскрытием `[Sn] → title, url` добавляется в блок 25.

### Режим без источников

Пустой или отсутствующий `TAVILY_API_KEY` перестаёт быть тихим: пишется предупреждение в
`quality_issues` playbook-а, генерация переходит в режим «без внешней статистики», и
`validateUnsourcedStatistics` режет любое точное внешнее число.

## 4. Маркировка примеров

Продуктовое решение: конкретные примеры остаются — они делают документ полезным «из коробки», — но
обязаны быть однозначно отличимы от корпоративной правды.

### Правило для блоков

> Company-specific значение, не подтверждённое загруженным корпусом или ответом пользователя
> (оклад, бонус, ARR, бюджет, имя человека, название внутреннего инструмента), остаётся
> конкретным, но обязано нести единый маркер: `(пример — заменить)` для русского,
> `(example — replace)` для английского. Маркер ставится сразу после значения, в той же строке или
> ячейке таблицы.

Все помеченные значения дополнительно перечисляются в чеклисте внедрения (блок 26) как позиции для
калибровки перед публикацией.

Формулировка «use a realistic invented example and mark it as an example» из текущих промптов
заменяется на это правило с явным форматом маркера. Существующий запрет на сырые плейсхолдеры
(`[Name]`, `{value}`) сохраняется без изменений.

## 5. Контекст предыдущих блоков (`prior_blocks_digest`)

Строится детерминированно из `state.generatedBlocks` перед вызовом каждого группового генератора
и содержит:

- анти-цели из блока 2 (полный список);
- все числовые обязательства, уже произнесённые в принятых блоках, в формате `метрика: значение`;
- названные роли, инструменты и лица;
- обещанные ритмы взаимодействия (ежедневно / еженедельно / ежемесячно).

Ограничение по размеру: не более 3500 токенов; при превышении усечение по приоритету — анти-цели
и числовые обязательства сохраняются всегда.

Потолок 3500 выбран замером на 14 сохранённых завершённых плейбуках (mc2-u3t9n): это наименьшее
значение, при котором числовые обязательства доходят не ниже 97% в каждой группе. При 1500 в
последней группе доходило 40% чисел и ни одного ритма. Цена — около +3000 входных токенов на
плейбук, распределённых по пяти вызовам генератора. Больший потолок покупает только ритмы, самую
низкоприоритетную из четырёх секций, и перестаёт ограничивать вообще.

Что именно считается числовым обязательством: число с компаратором (`≥`, `<=`, «не менее»),
с единицей (`%`, `×`, `ч`, `мин`, дни, недели, баллы), с валютой или со шкалой («4 из 5»). Номера
строк таблицы, нумерация списков, время суток, ссылки `[Sn]` и «Block N» числами не считаются.
Раньше правилом было «в строке есть цифра», под которое попадала треть всех строк.

Ритмы ищутся по основам, а не по целым словам: `\b` — граница ASCII-слова и на кириллице не
срабатывает, из-за чего секция ритмов была пуста в каждом русском плейбуке (mc2-539pz).

Причина: сейчас группа 2 физически не может свериться с анти-целями группы 1, потому что в промпт
передаются только `spec_json`, `content_language` и заголовки (RC-2).

### 5.1 Одна секция на группу

Digest строит одну секцию с заголовком `For every output block in this group:` — все target-блоки
группы получают одни и те же строки. Учитываются только блоки в состоянии `generated`;
незавершённый блок не может попасть в анти-цели, матрицу полномочий, числа или ритмы.

Границы по адресату здесь нет намеренно (mc2-923ku). Четыре секции digest — это защита от
противоречий внутри одного собранного документа, а не подсказка «о чём не писать»; противоречие
запрещено везде, независимо от того, делят ли блоки читателя.

### 5.2 Ссылки между блоками

Блок может назвать другой блок, только если **каждый** читатель первого читает и второй —
подмножество, а не пересечение. `block_26` (manager+hr) не может сослаться на `block_5`
(employee+manager), хотя руководитель читает оба: HR-читатель `block_26` блока 5 не получит.

Промпту это передаётся переменной `citable_blocks_md`: для каждого выходного блока группы —
перечень блоков, которые ему разрешено назвать. Называть остальные запрещено в любой формулировке,
включая описательную («раздел о профиле кандидата»).

Когда нужное содержимое лежит в блоке, который называть нельзя, действуют три правила (решение
владельца 2026-08-30, mc2-de3vu — расширять доступ по адресатам вместо этого решено НЕ делать, потому
что раздел слишком крупная единица доступа, а лишний читатель делает текст безадресным):

1. переносится **только нужная часть** — один порог, один уровень согласования, один владелец, — а не
   раздел целиком;
2. переносимое **пишется под читателей этого блока**: меняться может подача, но не существо. Каждое
   число, порог, уровень согласования, ритм и названное лицо остаются ровно как опубликованы;
3. если нужная часть — то, чего читателям этого блока видеть не следует, она **не пишется вовсе**.

Из этого же следует правило обращения: блок с несколькими читателями называет каждого там, где их
часть различается, а не уплощается в голос, который не подходит никому.

Правило AUTHORITY стало условным: ссылаться на блок 5, если он в списке разрешённых; иначе привести
уровень согласования дословно, не называя блок.

Замер до правки (14 сохранённых плейбуков): 72% перекрёстных ссылок HR-представления вели в блок,
которого у HR нет; у руководителя 19%, у сотрудника 11%; затронуты все 14 плейбуков. Метод и разбор:
`docs/career-playbook/2026-08-30-role-guide-views-measurement.md` (mc2-c0pdn).

Раньше секция строилась отдельно на каждый target и отбрасывала блоки чужого представления. После
снятия фильтра по адресату секции стали побайтово одинаковыми — замер на 14 сохранённых завершённых
плейбуках дал 70 из 70 групп, — а потолок продолжал делиться на число target-ов, то есть оплачивал
копии. В `group_6_wrap` до модели доходило 3% собранных строк матрицы решений блока 5, ни одного
числового обязательства, и 66 из 84 target-ов теряли уже опубликованную анти-цель. Одна секция на
группу при том же бюджете даёт 100% анти-целей и 100% матрицы решений во всех группах (mc2-4win5).

`block_boundaries[block].do_not_repeat` не является модельным решением. Каноническая нормализация
полностью перезаписывает поле списком тем блоков, которые делят с текущим хотя бы одно
представление и не пересекаются с ним по нормализованным aliases. Поэтому два разных ответа модели
дают один и тот же итоговый запрет, а тема блока из чужого представления в него не попадает.

Требования к реализации проверок:

- Каждая проверка — чистая функция без сетевых вызовов, покрытая юнит-тестами на позитивном и
  негативном примере из реального прогона (`artifacts/career-playbook-quality/career-playbook.md`).
- Ложное срабатывание дороже пропуска только для `validateExampleMarking`: там допускается
  консервативный список паттернов, чтобы не помечать бенчмарки со ссылкой.
- Проверки не смотрят внутрь fenced-блоков Mermaid и кода.

Единица сравнения — элемент перечисления (`enumerationSegmentAt`), а не строка. Строка регулярно
несёт несколько метрик со своим числом у каждой: «CSAT <85%; First response time >30 мин; Average
resolution time >48 ч». Замер 2026-09-01 по 13 сохранённым плейбукам: **все пять** доживших до
документа `metric_conflict` оказались числом соседа — 90% плановых коучингов, приписанные team quota
attainment (638ed691, block_21 и block_26), и вес зоны ответственности «(10%)» в заголовке,
приписанный team retention (4e355bf4, block_3). Три из этих блоков выбрали потолок регенераций на
претензии, исправить которую нельзя. После правки: 5 → **0**, находки по ритмам, срокам и владению
рампой не изменились ни в одном прогоне (mc2-tub8q).

Разделителем перечисления не является запятая перед цифрой: в русском это десятичная точка. Прогон
7bd743bd писал красную зону как «Customer effort score >3,5» — запятая резала число пополам, и
остаток «>3» читался как цель, конкурирующая с реестровой «<=2,5». Таблица при этом остаётся одним
элементом: `|` разделителем не считается, поэтому стандартная форма KPI-таблицы (метрика в первой
колонке, цель в третьей) по-прежнему читается — именно на этом сломалась более ранняя попытка
сузить сравнение до ячейки.

### 6.1 Семантический повтор

Финальный судья дополняет чистые проверки одним детерминированно маршрутизированным, но
provider-backed сравнением Jina-эмбеддингов:

- полные тексты блоков сравниваются только для пар с общим представлением;
- абзацы длиной не менее 100 нормализованных символов сравниваются только внутри своего блока, и
  только если их форма не решается по тексту как параллельная (см. «Что отгружено» ниже);
- cosine similarity `>= 0.85` создаёт находку `contradiction`: `critical` для межблочной пары — у
  обоих участников, чтобы существующий ledger мог направить регенерацию, — и `warning` для пары
  абзацев внутри блока;
- прод-порог хранится в `nodes/repetition-thresholds.ts` и выбран по baseline 2026-08-29:
  8/6 594 пар блоков внутри представлений и 18/6 829 пар абзацев были слишком близки;
- приёмочный `scripts/measure-playbook-repetition.ts` держит собственные копии порога, минимальной
  длины абзаца и карты адресатов (`BASELINE_AUDIENCE_BLOCKS`), потому что фазу 0 мерили до того, как
  карта появилась в проде. Копии сверены и совпадают, но они не связаны: смена прод-порога не
  доедет до измерителя, и отчёт покажет зелёное для порога, которого в проде уже нет (`mc2-spkoj`).

Проверка выполняется один раз на финальном полном судье; групповые окна её не вызывают. Векторы
неизменившегося текста повторно используются только внутри того же playbook через ограниченный
LRU-кеш с ключом `playbookId:SHA256(text)`. Расход каждой Jina batch-записи идёт узлом
`semanticRepetition` в `career_playbooks.cost_breakdown`.

Гейт различает два исхода, и это разные вещи.

**«Не смогли измерить»** — провайдер недоступен после ограниченных retry. Финальный graph
останавливается: playbook получает статус `failed` и не может стать `completed` без semantic-гейта.
Ошибка переносит уже полученные `semanticRepetition` node costs до handler-а, а handler сохраняет
их в `career_playbooks.cost_breakdown`. Недоступность провайдера не является обходом контракта и не
стирает уже понесённый расход.

**«Измерили, нашли, за две попытки не исправили»** — playbook завершается, а пара пишется
предупреждением в `generation_warnings`. Ронять здесь нечего: документ известен целиком, и
единственная помеченная пара не стоит остальных двадцати шести блоков. 2026-08-30 прогон
`1a4a9ccb` доказал цену прежнего поведения — одна пара в `block_9` уничтожила 27 готовых блоков и
$0.08711 оплаченной генерации, из которых в базу дошли $0.00018.

Предупреждение обязано нести измерения: обе стороны пары, косинус и порог. Тот же прогон показал,
почему — гейт назвал только `block_9`, и установить, с чем именно он совпал, было нельзя, не
оплатив второй прогон. Форма `for <blockIds>;` в тексте предупреждения несущая:
`collectWarningQualityIssues` разбирает именно её, чтобы привязать претензию к блокам.

**Решено 2026-09-02: сравнение абзацев ловит параллельную структуру, а не повтор (mc2-de6fe).**
Замер 2026-09-01 по всему сохранённому корпусу — 24 плейбука, 13 469 внутриблочных пар абзацев,
эмбеддинги через клиент пайплайна и его же `splitCareerPlaybookSemanticParagraphs`:

| полоса    |   пар |
| --------- | ----: |
| < 0.80    | 13395 |
| 0.80–0.85 |    52 |
| 0.85–0.88 |    14 |
| 0.88–0.90 |     2 |
| 0.90–0.95 |     6 |
| ≥ 0.95    |     0 |

Порог переходят 22 пары, из них 15 в пяти блоках, чей контракт — таблица или параллельный чеклист
(block_11 ×5, block_4 ×4, block_14 ×3, block_18 ×2, block_26). Прочитанные вручную двенадцать
верхних — не повтор: два разных спринтовых гейта под одинаковой подписью, гейт 60 дней и гейт 90
дней, две ветки карьерной лестницы в двух таблицах с общей шапкой, чеклист руководителя и чеклист
сотрудника. Поэтому регенерация и не помогает: модель переписывает содержание, а меряется общая
рамка, которую она обязана сохранить.

Что рамка и есть сигнал — проверено: пересчёт тех же 22 пар со снятой markdown-разметкой и общей
ведущей подписью опускает **15** ниже порога, включая все три критикала, ради которых задача
заводилась (`cc12dccc block_11` 0.8627 → 0.6800, `db9d3ff9 block_11` 0.8565 → 0.7266,
`db9d3ff9 block_21` 0.8582 → 0.6445).

Кандидат «нормализовать markdown перед эмбеддингом, сохранив все слова» **измерен и отклонён**:
22 → 15, но он гасит 10 и поднимает 3 новых, а часть выживших толкает выше
(`1acebc5b block_4` 0.8748 → 0.9365). Он перераспределяет, а не разделяет: укорачивание текста
концентрирует общую рамку вместо того, чтобы её убрать.

**Что отгружено.** Повторный замер 2026-09-02 на 28 плейбуках дал 24 пары выше порога, и все 24
прочитаны вручную: **ровно одна** — настоящий повтор (`a03dfb46 block_9`: одна таксономия делегирования
ИИ, изложенная двумя таблицами с переименованными колонками). Отдельно посчитаны находки, которые
проверка когда-либо заводила в живых прогонах, — их **шесть** на весь корпус, и ни одна из них не
повтор:

| плейбук  | пара           | косинус | что это на самом деле                        | снимается правилом |
| -------- | -------------- | ------: | -------------------------------------------- | ------------------ |
| cfa66ada | block_11 ¶4/5  |  0.8704 | две ветки лестницы, эксперт против директора | нет                |
| db9d3ff9 | block_11 ¶4/5  |  0.8559 | две таблицы лестницы с общей шапкой          | общая шапка        |
| db9d3ff9 | block_21 ¶4/13 |  0.8576 | две записи под подписью «Ранние сигналы:»    | общая подпись      |
| cc12dccc | block_11 ¶4/5  |  0.8632 | две таблицы лестницы с общей шапкой          | общая шапка        |
| 4e355bf4 | block_14 ¶2/5  |  0.8674 | список первых побед против плана по дням     | нет                |
| d5137bc5 | block_11 ¶3/4  |  0.9059 | две таблицы лестницы с общей шапкой          | общая шапка        |

Отсюда два изменения, каждое со своим основанием:

1. **Пара не сравнивается вовсе**, если её форма решается по тексту: две таблицы с одинаковой шапкой
   и различающимися строками, либо два абзаца с одинаковой ведущей подписью. Снимает 9 пар из 24 и
   четыре критикала из шести. Обе проверки — чистые функции, вызова к провайдеру не стоят.
2. **Внутриблочная находка понижена до `warning`.** Из шести заведённых за всю историю верна ноль;
   оставшиеся после первого правила 15 пар — по-прежнему параллельная структура (гейт 60 дней рядом
   с гейтом 90 дней, чеклист руководителя рядом с чеклистом сотрудника, недельные обязанности рядом
   с месячными). Регенерация на таком сигнале переписывает верный текст и не может его удовлетворить,
   не сломав параллельную форму, которой требует контракт. Находка остаётся видимой и перестаёт
   тратить попытку.

Межблочное сравнение остаётся `critical`: это другое измерение — два целых блока внутри общего
представления, — и против него данных нет.

Побочно вскрылось, что `verdictFromIssues` отправлял на регенерацию всё, что не `info`, то есть и
`warning`. Из-за этого собственная подсказка `validateContractLeakage` («это предупреждение, а не
триггер регенерации») была неправдой о коде под ней. Теперь на обоих путях — детерминированном и
LLM — регенерацию вызывает только `critical`.

Нормализатор выше по-прежнему не отгружать.

### 6.2 Сколько прогонов нужно, чтобы число что-то значило

Этот трек три недели сравнивал прогоны по количеству критикалов (таблицы вида «25 → 9 → 7»).
Измерение 2026-09-02 показывает, что при одном прогоне на плечо это шум, а не мера (mc2-x15bk).

Узел `finalProofreader` переигран 32 раза на двух **побайтово одинаковых** документах:

| документ      | плеч | критикалов                               | размах |
| ------------- | ---: | ---------------------------------------- | -----: |
| 609b5a60 (en) |   16 | 5 9 3 9 10 8 12 8 7 7 7 11 7 8 11 6      |   3–12 |
| cfa66ada (ru) |   16 | 8 8 12 11 4 6 11 11 12 12 6 5 12 8 12 12 |   4–12 |

Различаются и блоки, уходящие в `needs_regeneration`. Это не разброс вокруг числа — это разные
ответы на один и тот же вход.

Отсюда правила чтения:

- **Детерминированные проверки — годная мера.** На одном тексте они дают одно число. Все закрытия
  этого трека, опирающиеся на них (`validateContractLeakage`, `validateScriptSplice`,
  `validateCadenceConsistency`, `validateMilestoneConsistency`, `validateCrossViewReference`),
  воспроизводятся на любом количестве прогонов.
- **Судейские и вычиточные категории** (`contradiction`, `invented_number`, `metric_conflict`)
  требуют не менее **восьми** плеч на сравниваемую сторону. Дешёвый способ — переигрывать узел на
  закреплённом документе: $0.002 против $0.10 за полный прогон, то есть 16 плеч стоят дешевле
  одного прогона.
- **Прогоны «до» и «после» 2026-09-02 несравнимы по общему числу критикалов.** У `422471a2` и
  `208746e3` в `quality_issues` ноль записей от `final_proofreader` — не потому что их не было, а
  потому что до mc2-nfyyo они не сохранялись. Слева одно слагаемое, справа два.

Таблица сравнения прогонов без указания числа плеч на сторону — не измерение, и читать её как
измерение нельзя.

| `wrong_language`         | без изменений | Пользовательский текст не на целевом языке                                                                                                             |
| `unresolved_placeholder` | **сужена**    | Остался сырой плейсхолдер в скобках. Маркер примера плейсхолдером НЕ является — см. 7.1                                                                |
| `invented_number`        | **сужена**    | Company-specific число заявлено как факт без подтверждения. Окно наблюдения — сколько симптом должен продержаться, — не является таким числом; см. 7.3 |
| `metric_conflict`        | **новая**     | Значение метрики расходится с `metric_ledger`                                                                                                          |
| `unsourced_claim`        | **новая**     | Точная внешняя статистика без ссылки на `evidence_ledger`                                                                                              |
| `stale_date`             | **новая**     | Абсолютная дата вне года `generated_on`                                                                                                                |
| `unmarked_example`       | **новая**     | Company-specific пример в universal-режиме без маркера                                                                                                 |

**Некритичные:** `style` и любая категория, которую модель не проставила. Правило «`style` никогда
не ведёт к регенерации» сохраняется вместе с защитным понижением
`downgradeNonTaxonomyCriticalIssues`.

### 7.1 Маркер примера — контрактный вывод, а не плейсхолдер

Прогон `d5137bc5` (2026-08-30). Все восемь его критичных `unresolved_placeholder` указывали на
маркер, который контракт **требует** ставить у любого непроверенного значения компании:

> «Tool entries contain unresolved replacement instructions such as "example — replace with the
> company's actual CRM".»

Про блок 26 судья даже написал «intentionally lists many» — и всё равно завёл critical. Восемь
critical — восемь тикетов на регенерацию, крупнейший источник впустую потраченных переписываний в
прогоне. Выполнить такую претензию можно единственным способом: убрать маркер, после чего блок
немедленно становится дефектом `unmarked_example`. Две нормы одного контракта тянули в разные
стороны, и судья восемь раз разрешил их не в ту сторону.

Правило маркера работает в ОДНУ сторону: дефект — его отсутствие, наличие — никогда. Уточнение,
называющее что именно заменить, разрешено; детерминированная `validateExampleMarking` уже принимает
такие варианты.

**Поправка, найденная на ревью.** Первый вывод «детектор корректен, трогать не нужно» был неверен.
`shouldTreatBracketAsFillableField` был белым списком из шести меток и на всех 19 сохранённых
playbook находил **11 совпадений из 158**: 13 документов отдали читателю сырой плейсхолдер —
`[Заполняется]`, `[Enter date]`, `[поле для заполнения]`, `[ФИО, должность]`, а в блоке 14 дважды
`[research: onboarding insights]`, то есть имя переменной промпта, попавшее в таблицу онбординга.

Правило инвертировано: скобка в тексте для читателя — поле для заполнения, если это не разметка
(inline- или reference-ссылка, ссылка на источник `[Sn]`, чекбокс). На том же корпусе инвертированное
правило даёт 158 из 158 и ни одного ложного срабатывания — доказательство, которого у белого списка
никогда не было.

Это важно вдвойне из-за фильтра ниже: он делает детектор authority, поэтому его слепое пятно молча
превращается в дефект, о котором никто не сообщит.

Закреплено фильтром, а не только промптом. `downgradeUnconfirmedPlaceholderIssues`
(`nodes/cross-block-judge.ts`) понижает до warning любой critical категории
`unresolved_placeholder`, который `findUnresolvedFillablePlaceholders` не подтверждает по тексту
блока. Владелец вопроса — детектор, он и решает; промпт судьи объясняет то же самое словами.

### 7.2 Категория описывает найденное, а не обязывает искать

В том же прогоне три претензии из 25 в собственном описании сообщали, что проверка пройдена:
«NO ISSUE FOUND», «this is NOT a language error», «They ARE marked as examples». Категории
`wrong_language`, `format_minimum`, `invented_number` и `unmarked_example` дали ровно по одной
претензии каждая — форма модели, идущей по списку как по чек-листу.

Промпт этого не требовал, но и не запрещал: строка «Every issue MUST include a category field»
читается как «на каждую категорию нужна запись». Заменена на прямое утверждение, что пустой список
issues — правильный ответ для чистой группы, и что претензию, чьё описание заключает «проблемы
нет», заводить нельзя.

### 7.3 Окно наблюдения принадлежит блоку 17, порог — реестру

Прогон `208746e3` (2026-09-01, ru) отгрузил критикал `invented_number` на фразу блока 17: «если она
три дня подряд фиксирует одни и те же мёртвые записи без реакции, это флаг процесса». Судья прав по
букве правила, и блок сам с этим правилом согласен — его собственное вступление обещает, что
«пороговые значения берутся только из светофоров ключевых показателей (Block 6) и не
переопределяются здесь». То есть блок пообещал не задавать порог и задал.

Причина обещания — формулировка в промпте группы 4: «Warning thresholds come from the metric ledger,
not from new numbers». Абсолютная, и блок её добросовестно пересказал читателю (что само по себе
утечка инструкции автору). Но запретить окно наблюдения целиком нельзя: блок красных флагов тогда не
может сказать, когда флаг становится флагом.

**Решение (2026-09-02, mc2-afoz6).** Реестр владеет значениями метрик и их порогами. Он не владеет
тем, сколько симптом должен продержаться, прежде чем считаться флагом: «три ревью подряд», «две
недели без ответа» — это чтение сигнала, а не цель, и ни один реестр такого окна не несёт. Правило
переписано на обеих сторонах одновременно — в промпте группы 4 и в определении `invented_number` в
промпте судьи, — потому что односторонняя правка не снимает конфликт, а переносит его: судья
продолжил бы заводить критикал на текст, который генератору разрешён.

## 8. Редакторские правила

### 8.1 Рубрика решений (блок 5)

Одна метка «one-way / two-way door» заменяется четырьмя независимыми осями:

| Ось                       | Значения                                                       |
| ------------------------- | -------------------------------------------------------------- |
| Обратимость               | обратимо / обратимо с издержками / необратимо                  |
| Радиус поражения          | команда / функция / компания / клиент                          |
| Контрактные обязательства | нет / есть срок / есть штраф                                   |
| Уровень согласования      | самостоятельно / уведомить / согласовать / решает руководитель |

Смена стадий CRM и выбор вендора классифицируются как «обратимо с издержками», а не как
необратимые. Найм и увольнение остаются высококонсеквентными.

### 8.2 Карьерная лестница (блок 11)

- Следующий уровень не может совпадать по смыслу с текущим: «CRO → Chief Revenue Officer /
  President of Revenue» запрещено.
- «Senior <роль> (IC)» запрещено для роли с подчинёнными, если по контексту это управленческая
  позиция.
- Каждый переход несёт критерий продвижения и срок в относительных единицах.

### 8.3 Точность формулировок метрик

Точность прогноза описывается через абсолютную ошибку, а не через «точность > ±20%». Формулировка
вида «accuracy consistently >±20%» смешивает точность с отклонением и запрещена.

## 8bis. Правила v2 — из редакторского чтения прогона 2026-08-11

Прогон закрыл все четыре формализованных класса дефектов и получил 3.9 / 5 при пороге 4.0. Ниже —
правила для шести дефектов, которые нашло только чтение целого документа. Полный разбор:
`.codex/stages/mc2-db696.110/evidence/quality-review.md`.

Общий принцип тот же, что дал результат в v1: **что можно собрать кодом — собирается кодом, а не
запоминается моделью.** Раздел «Источники» работает именно потому, что собирается из реестра, а не
пишется моделью через 900 строк после первой цитаты.

### 8bis.1 Полномочия: блок 5 — канонический источник

Блок 5 для полномочий — то же, чем реестр метрик стал для чисел. В прогоне блок 5 разрешал нанимать
«act alone — approval не требуется», блок 16 описывал workflow «culture-fit debrief → CRO sign-off →
offer», блок 24 писал «Full authority | CRO for exceptions». Три утверждения об одном полномочии.

Правила:

1. `prior_blocks_digest` несёт строки матрицы решений блока 5 отдельной секцией — решение, уровень
   согласования, обратимость. Так блоки 16 и 24 физически видят, что уже обещано.
2. Блок, который упоминает решение из блока 5, **ссылается** на него и не переписывает уровень
   согласования своими словами.
3. Новая детерминированная проверка `validateDecisionAuthorityCoherence` работает **внутри** блока 5
   и ловит внутреннюю несогласованность строки: решение, помеченное `irreversible` с радиусом
   `function`, `company` или `customer`, не может иметь уровень `act alone`. Это ловится
   однозначно, потому что все четыре оси — фиксированные словари.
4. Категория судьи `contradiction` явно называет конфликт полномочий как свой случай.

### 8bis.2 Чеклист калибровки собирается кодом

В прогоне блок 26 перечислил шесть позиций и не назвал ни одной из семи помеченных денежных сумм —
инструмент, который делает пометки действенными, не указывал на то, что важнее всего заменить.

Правило: таблица «Что заменить перед публикацией» **собирается детерминированно на финальной сборке**
сканированием собранного документа по маркеру примера — тем же приёмом, что и раздел «Источники» из
реестра источников. Модель больше не отвечает за полноту этой таблицы.

- Каждая строка: блок, значение, окружающий фрагмент до 120 символов.
- Строки отсортированы по порядку блоков.
- Если маркеров нет — секция не добавляется.
- Регресс-тест: число строк таблицы равно числу маркеров в собранном документе.

Существующий текст блока 26 от модели сохраняется, сгенерированная таблица заменяет её собственную
попытку перечислить значения.

### 8bis.3 Ничего из контракта не попадает в текст читателю

В прогоне блок 6 напечатал: «Do not use "accuracy above +/-20%" language — always measure forecast
quality as absolute error». Это указание автору документа, показанное менеджеру по продажам. Плюс 23
внутренних идентификатора `block_5`, `Block_6` рядом с корректной формой «Block 8».

Правила:

1. В блоке общих правил промпта добавляется явная строка: правила описывают, **как писать**, и
   никогда не пересказываются в выходном тексте.
2. Перекрёстные ссылки — только в человекочитаемой форме «Block 8». Финальная сборка
   детерминированно нормализует `block_8`, `Block_8`, `block 8` к единой форме.
3. Детерминированная проверка `validateContractLeakage`: в тексте нет snake_case-идентификаторов
   блоков и нет предложений, обращённых к автору документа (характерный маркер — цитирование
   запрещённой формулировки внутри кавычек рядом с «do not use … language»).

**Дополнение 2026-08-30 (прогон `d5137bc5`).** Появилась вторая форма утечки, которую узкий
паттерн не ловил: модель объясняет читателю устройство самого документа. Три случая дословно:

- `block_26`, пункт чек-листа для руководителя: «Do not restate these levels in different words
  anywhere else in this guide.»
- `block_17`: «does not restate the full metric definitions — the table above carries the exact
  thresholds this block needs».
- `block_13`: «two cadences — do not merge them … this block does not redefine either one».

Источник — формулировка в промпте: секция REFERENCES объясняла правило через его последствие
(«a second wording is how one decision came to have three different approval levels»), а модель
приняла объяснение за содержание, достойное изложения. Правило должно **управлять письмом**, а не
попадать в него; обоснование правила в промпте не нужно вовсе. Родственный урок: лицензия в
промпте поднимает счётчик («about one per section is plenty» подняла число врезок 3.0 → 5.0).

`AUTHOR_INSTRUCTION` расширен под эту форму. Глаголы «restate», «reword», «paraphrase» всегда
про формулировку, поэтому запрет ловится сам по себе; «redefine» и «repeat» имеют честное
читательское употребление и считаются утечкой только когда подлежащее — часть документа. «In other
words» и «другими словами» — нормальные обороты и не ловятся.

**Дополнение 2026-09-01 (прогон `422471a2`, mc2-o29g8).** Источник этой формы утечки найден и
устранён. Прогон отгрузил в `block_10`: «Block 5 lists exactly who holds the final call on each …
this section does not restate those approval levels». Прогон `validateContractLeakage` по всему
сохранённому корпусу даёт **шесть** утечек в трёх документах, и пять из них — про пересказ
опубликованного факта; шестая, `d5137bc5 block_26`, повторяет инструкцию почти дословно.

Причина — заголовки секций `prior_blocks_digest`. Каждый из пяти нёс правило письма внутри данных,
которые модель читает:

- «Decision authority already published in Block 5 (cite it; **never restate an approval level in
  other words**):»
- «Numeric commitments already published (**do not restate with a different value**):»
- «Cadences already promised (**restate none of these with a different frequency**):»

Методика группы 5 нигде не упоминает Block 5, поэтому `block_10` мог узнать о матрице полномочий
только из дайджеста — и узнал под этим заголовком.

Правило: **заголовок дайджеста называет, что лежит в списке, и больше ничего.** Все правила письма
уже есть в `GROUP_OUTPUT_CONTRACT` (секции NUMBERS, RHYTHMS, DEADLINES, CONSISTENCY), где они стоят
среди правил построения, а не рядом с содержанием. Единственное правило, которого там не было —
опубликованный шаг карьерной лестницы сохраняет своё название — переехало в CONSISTENCY.

Запрет не добавлялся: `ae0dbfb83` уже показал, что промпт, который только запрещает, становится
третьей инструкцией по одному вопросу. Убирается триггер. Регресс ловит сам
`validateContractLeakage`, и тест `prior-blocks-digest.test.ts` прогоняет дайджест через него так,
как если бы дайджест был содержимым блока: если он был бы утечкой внутри блока, модели есть что
скопировать.

### 8bis.4 Цитата должна подтверждать утверждение, а не просто существовать

Сейчас проверка убеждается, что `[Sn]` существует и разрешается в запись реестра. В прогоне «87% of
sales organisations now use AI [S9]» прошло, хотя никто не проверял, есть ли 87% в источнике.

Правило: `validateUnsourcedStatistics` дополняется сверкой значения. Если предложение содержит точное
число и ссылку `[Sn]`, это число (с нормализацией формата) должно встречаться в `claim` записи `Sn` —
там лежит извлечённый фрагмент источника. Не встречается → `unsourced_claim`.

Это дёшево и честно: реестр уже хранит текст фрагмента, сверять есть с чем. Полную семантическую
проверку это не заменяет и не претендует.

Дополнительно `evidence_ledger` получает поле `source_kind` (`research` / `vendor` / `media` /
`unknown`), выводимое по домену. Оно печатается в разделе «Источники», чтобы читатель отличал
исследование от вендорского блога — все четыре источника прогона были вендорскими.

### 8bis.5 Внутренняя связность числовых шкал и расписаний

Два дефекта, которые ловятся только смыслом, — правила промпта, не проверки:

- **Непрерывность шкал.** Ступенчатая шкала выплат не может иметь разрыв на границе диапазона. В
  прогоне жёлтая зона шла «от 50% при 75% до 90% при 89%», а зелёная платила 100% при 90%: один
  пункт достижения стоил десяти пунктов бонуса.
- **Ритмы помещаются в день.** Обещанная в блоке 4 периодичность должна укладываться в слоты
  расписания блока 13 при **верхней** границе числа подчинённых. В прогоне 6-12 подчинённых против
  десяти слотов в неделю.

### 8bis.6 Проход вычитки по собранному документу

Владелец снял ограничение по времени: качество важнее скорости. Это возвращает отложенный проход.

Новый узел после `finalAssembler`, до `finalJudge`: один вызов по **собранному** документу, который
ищет то, что окно группы увидеть не может — противоречие смысла между далёкими блоками,
несогласованность полномочий, разрыв шкалы, инструкцию автору в тексте, языковые и грамматические
дефекты. Возвращает находки в существующей схеме вердикта; они идут в тот же путь регенерации.

Проход обязан видеть весь документ (~30 тыс. токенов входа) — это его смысл. Модель — сильная;
маршрутизация по размеру уже существует (`preferFallbackModelAboveTokens`).

Вердикт запрашивается схемой, а не прозой — тем же механизмом, что и у судьи
(`nodes/structured-verdict.ts`). До 2026-09-01 проход просил JSON текстом и разбирал ответ цепочкой
починки. На пяти английских прогонах это работало; первый русский прогон (db9d3ff9) потерял вычитку
целиком: три вызова, три неразбираемых ответа, три предупреждения, о которых читатель не узнаёт.
Причина — не язык, а то, что русское руководство цитирует: блок 22 называется
`README: "Как со мной работать"`, модель честно процитировала заголовок внутри строки JSON, и
внутренние прямые кавычки закрыли строку на четыре слова раньше. Ни одна стратегия починки не
отличает кавычку, закрывающую значение, от кавычки внутри него; ограниченный декодер её не породит.

Два следствия зафиксированы вместе с этим:

- пропущенный проход всё равно оплачен. Чек стоимости обязан нести вызовы, которые **ответили**, а не
  только оборванные попытки: db9d3ff9 оплатил три ответа, не попавших в `nodeCosts` вообще;
- запрос схемы принимает не каждый эндпоинт модели, и наш выбор эндпоинта об этом не знал.
  `pickCheapestUntriedEndpoint` сортировал по цене, здоровью, тарифу и пропускной способности —
  но не по тому, что вызов вообще просит. У `z-ai/glm-5.3-flash` 19 живых эндпоинтов, схему
  принимают 12, и три самых дешёвых (все по $0.075/M) — из тех семи, что не принимают, тогда как
  четвёртый по той же цене принимает. Пин в такой эндпоинт даёт `404 No endpoints found`: это не
  откат на соседа, а потраченная попытка ради того, что каталог уже сообщил. Теперь выбор фильтрует
  по `supported_parameters`, и «дешевле всего» означает «дешевле всего среди тех, кто отвечает на
  заданный вопрос».

Модель прохода — `deepseek/deepseek-v4-flash-0731` с 2026-09-01, та же, что у судьи. Проход стоял на
прозаической `z-ai/glm-5.3-flash` с 20260826200000, и та же миграция записала правило, которое эта
строка нарушала: «вердикт — не проза» (поэтому судьи остались) и «эти фазы отдают JSON, который
разбирает пайплайн, а glm игнорирует строгий json_schema». Проход — и то, и другое: он не пишет ни
одного предложения, которое откроет читатель, он возвращает `CareerPlaybookJudgeVerdict`. В список
прозы он попал по названию. На реальной форме вызова (33 тыс. токенов входа, ~3 тыс. находок) это ещё
и втрое дешевле: ~$0.0019 против ~$0.0050 у glm на тех его эндпоинтах, которые принимают схему.

Замер после переключения, четыре прогона по одному и тому же документу: находок 10–12, из них
критичных 2, 3, 11 и 12 — против 0 и 2 у glm. Верхняя граница ущерба ограничена
`CAREER_PLAYBOOK_MAX_PROOFREADER_REGENERATIONS = 3` и шлюзом авторитета, который понижает
неподтверждённые критикалы LLM.

**Модель не меняем (решено 2026-09-02, mc2-r2468).** Разбор, ради которого вопрос заводился, привёл
к другому вопросу: вердикт этого узла невоспроизводим у обеих моделей (раздел 6.2 — 32 плеча,
размах 3–12 критикалов на неизменном входе). «glm тише» — это одно плечо против одного, то есть не
измерение, а «тише» и не значит «вернее». Возврат к glm противоречил бы и решению о структурированных
выводах, и тому, что выигрыш нечем показать. Открытым остаётся не выбор модели, а метод сравнения.

**Поправка 2026-09-01.** Ранее здесь стояло, что повторяющаяся тема настоящая: «блок 13 ставит в
ежедневное расписание встречи, которые реестр ритмов объявляет еженедельными». Это неверно. Ячейка
блока 13 читается «| 10:30-12:00 | Индивидуальные встречи с сотрудниками (1:1) | **Еженедельно** с
каждым прямым подчинённым; в другие дни слот отдаётся коучингу |» — реестр говорит weekly, блок
говорит еженедельно. Модель прочитала часовой слот в таблице рабочего дня как заявление о
периодичности. В другой выборке критикал `metric_conflict` открывается словами «соответствует
каденс-леджеру» и заводится всё равно.

Решать это по повторам одного документа нельзя — смысл прохода в документе, которого никто ещё не
видел, — а до 2026-09-01 прогон не сохранял ни одной находки прохода: `q_a_data.quality_issues`
собирается обходом `generatedBlocks` за `judge_verdict`, а проход по собранному документу вешать
вердикт не на что. Прогоны `422471a2` и `208746e3` оплатили проход и сохранили между собой одну
строку с именем блока. Теперь проход отдаёт находки через `qualityIssues` под собственным источником
`final_proofreader`, поэтому вопрос «шум или сигнал» отвечается из любого будущего прогона бесплатно
(mc2-nfyyo, mc2-r2468).

#### Проход получает опись разделов, а не пересчитывает их (mc2-jqvf4)

Как только находки прохода начали сохраняться, стало видно, что он выдумывает отсутствующие
разделы. Не однажды и не на одном языке — во всех трёх прогонах 2026-09-02:

| прогон   | язык | что заявлено                                                                  | тяжесть               |
| -------- | ---- | ----------------------------------------------------------------------------- | --------------------- |
| cfa66ada | ru   | «разделы 6–20 отсутствуют», плюс пять производных находок про block_5         | 1 critical, 5 warning |
| 609b5a60 | en   | «guide jumps from Block 9 to Block 18», «Block 16 не представлен», «Block 14» | 3 info                |
| d50da4b1 | en   | своя вариация той же формы                                                    | 1 critical            |

Все три документа содержат по 27 заголовков и все 26 нумерованных разделов подряд — проверено
шаблоном по сохранённому `final_markdown`. Само утверждение cfa66ada внутренне противоречиво:
«jumps from section 4 to section 5» — это не пропуск.

Причина структурная, не языковая. Блоки 5 и 26 несут калибровочную таблицу, которая называет другие
разделы по заголовку; проверить эти имена — значит вспомнить заголовки из 25–35 тыс. токенов
контекста. Модель угадывает и ошибается.

Поэтому она получает ответ: `buildCareerPlaybookDocumentOutline` собирает нумерованную опись
заголовков шаблоном по той же строке, которую промпт уже несёт, и опись не может с ней разойтись.
Промпт объявляет опись источником истины о полноте.

**Что этим измерением подтвердить нельзя, и это сказано прямо.** Переигрывание узла на сохранённом
документе не воспроизводит галлюцинацию ни разу — ни до правки, ни после (0 из 16 плеч в каждом
плече, оба языка). Переигрывание берёт `final_markdown`, то есть текст **после** финальных
регенераций, а живой узел видел сборку до них. Значит замерить эффект этой правки повтором нельзя,
и заявлять улучшение по числам нечестно. Основание правки — механизм: модель перестаёт угадывать
факт, который ей теперь дан. Цена измерена: вход растёт примерно на 11% (en $0.00227 → $0.00250,
ru $0.00333 → $0.00377 за вызов).

Вторая половина правки измерима и измерена. `needs_regeneration` — отдельный список, который модель
пишет от руки, и ничто не требовало его согласия с находками выше. На LLM-пути
`mergeJudgeVerdicts` выводит такой список из собственных критикалов судьи; у прохода этого не было.
На трёх сохранённых прогонах проход пометил `regenerate` 10, 11 и 6 блокам при 8, 7 и 2 блоках с
настоящим критикалом. Теперь `deriveProofreaderRegenerations` пересекает список с блоками, против
которых проход завёл `critical`. Пересечение не расширяет: блок с критикалом, который модель
сознательно не отправила на перегенерацию, остаётся неотправленным.

## 9. Бюджет генерации

| Параметр           | Текущее (прогон 2026-08-11) |          Цель |
| ------------------ | --------------------------: | ------------: |
| Стоимость          |                     $0.1226 |   ≤ **$0.35** |
| Время              |                      56 мин | не ограничено |
| Регенераций блоков |                          13 |           ≤ 6 |

**Изменение от 2026-08-11:** владелец снял ограничение по времени — «долгая генерация не проблема,
главное качество». Потолок в 25 минут снят; латентность остаётся наблюдаемой метрикой, но больше не
гейт приёмки. Потолок стоимости сохраняется как защита от разгона и поднимается до **$0.60**, чтобы
вместить проход вычитки по собранному документу (раздел 8bis.6).

Как достигается — см. раздел «Надёжность и бюджет» в
[плане работ](../plans/buzzing-jingling-oasis.md). Ключевое: устранение обрезки spec-builder
(19 минут) и снижение `timeout_ms` с 300 000 до 120 000.

Чек стоимости обязан фиксировать **неуспешные и оборванные по таймауту** попытки со стоимостью
`unknown`. Сейчас их в `costBreakdown` нет вообще, и приложение не может ни подтвердить, ни
опровергнуть, что провайдер выставит счёт за прерванные вызовы.

Полная процедура — в [плане приёмки](../plans/career-playbook/06-quality-acceptance.md).
Кратко:

| Измерение                         | База 2026-08-11 |     Порог |

| Обоснованность и прослеживаемость |           1 / 5 |       ≥ 3 |
| Решения и управление рисками      |           3 / 5 |       ≥ 4 |

| Обложка                           |           3 / 5 |       ≥ 3 |
| **Общая**                         |     **2.6 / 5** | **≥ 4.0** |

Жёсткие условия, не сводимые к баллам:

- Ноль критичных находок по пяти детерминированным проверкам.

- Ноль абсолютных календарных дат вне футера.
- Стоимость и время в пределах раздела 9.
