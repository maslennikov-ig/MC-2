# Career Playbook: план повышения качества генерации (спецификация v2)

## Context

11 августа 2026 сделали представительную живую генерацию Role Guide (фикстура Sales Manager B2B,
англ., universal-режим, без загруженных документов). Формально всё прошло: 27 блоков, PDF на 60
страниц, обложка, $0.123 из разрешённых $0.50. По существу — документ **не готов к публикации**:
редакторская оценка **2.6 / 5** (`.codex/stages/mc2-db696.105/evidence/quality-review.md`).

Ключевое: это не «модель плохо написала». Я прошёл весь тракт — промпты, граф LangGraph, судью,
регенератор, PDF-рендерер, роутинг моделей — и каждая находка ревью воспроизводится по коду как
структурный дефект. Часть контроля качества была **описана в исходной спецификации, но потерялась
при реализации**, часть — сломана поздними оптимизациями «меньше регенераций».

Цель работы: переписать спецификацию генерации так, чтобы согласованность, обоснованность и
качество вёрстки обеспечивались контрактом и детерминированными проверками, а не удачей модели.
Целевая планка следующего представительного прогона — **≥ 4.0 / 5** и PDF, пригодный к публикации.

### Принятые продуктовые решения

| Вопрос                                    | Решение                                                                                       |
| ----------------------------------------- | --------------------------------------------------------------------------------------------- |
| Недоказанные факты                        | Чиним web-research **и** детерминированно блокируем точную внешнюю статистику без источника   |
| Company-specific числа в universal-режиме | Конкретные примеры остаются, но каждый обязан нести явный маркер; даты — только относительные |
| Бюджет                                    | ≤ **$0.35** и ≤ **25 минут** на генерацию                                                     |
| Объём этой сессии                         | Документы + нарезка задач в Beads. Код не трогаем                                             |

## Карта причин (что именно сломано)

### RC-1. В спецификации нет числового реестра — источник всех конфликтов метрик

`focus_areas.primary_kpis: z.array(z.string())` хранит только **названия** метрик, без целевых
значений и порогов (`packages/shared-types/src/career-playbook.ts:825-831`). Каждая группа блоков
получает `spec_json` и придумывает пороги заново.

Отсюда все четыре конфликта из ревью. Показательно, что конфликт возникает **даже внутри одного
вызова**: block_3 и block_6 генерируются одним промптом group_2, и всё равно расходятся —
`career-playbook.md:46` даёт покрытие воронки ≥2×, `:87` даёт ≥3×. Значит одного «общего промпта»
недостаточно: нужен явный реестр чисел.

Дополнительно ревью недосчитало ещё один конфликт: `:646` («ниже 3x») против `:710` («ниже 4x»).

### RC-2. Генераторы блоков не видят уже написанный текст

`generateCareerPlaybookGroup` рендерит промпт только с `spec_json`, `content_language` и
заголовками (`group-generator.ts:475-479`). Поля `input.qaData` и `input.webResearch` принимаются в
сигнатуре, но в промпт не передаются вообще.

Следствие: группа 2 (обязанности) физически не может свериться с блоком 2 (анти-цели) из группы 1.
Отсюда находка ревью №3 — «не микроменеджерить активность» и одновременно «три апдейта по каждой
сделке до 10:00 + один разобранный звонок на каждого сотрудника ежедневно» (`:32,55-56`).
Полный текст видит только судья — то есть контроль есть, а профилактики нет.

### RC-3. Судья по конструкции не считает конфликт чисел критичным

В таксономии судьи `contradiction` определён как «противоречит RoleProfileSpec **или** повторяет
тему, закреплённую за другим блоком» (`career-playbook-prompts.ts:549-551`). Поскольку чисел в
спеке нет (RC-1), расхождение порогов между блоками формально не противоречит спеку → попадает в
`style`, а `style` **никогда** не ведёт к регенерации (`:555` и гейт в
`cross-block-judge.ts:308-316`).

Категория `invented_number` ограничена «company-specific числом, квотой, бюджетом или дедлайном»
(`:553`) — рыночная статистика «90-95% точность ИИ», «28% response rate», «95% еженедельно / 65%
ежедневно» под неё не подпадает. Судья пропускает их корректно, по инструкции.

Подтверждение из run-record: два вызова `crossBlockJudge` вернули по 29 output-токенов — то есть
пустой вердикт «всё хорошо» на группах, где ревью потом нашло конфликты.

### RC-4. Источники теряются по дороге

- Клиент Tavily: `search_depth: 'basic'`, `max_results: 5`, таймаут **5 секунд**
  (`rag/web-research.ts:36,137-140`); при незаполненном ключе тихо возвращает `[]` (`:120-127`).
- Результаты уходят **только** в промпт spec-builder (`spec-builder.ts:150-153`).
- В промпты групп URL не передаются ни в каком виде. `research.sources` может попасть в блоки
  только если модель сама перепишет его в spec JSON.
- Требования цитировать в промптах групп нет.

Итог: в сгенерированном markdown **ноль** markdown-ссылок (проверено). При этом в исходной
спецификации требование было: «Russian language: "По данным {source}..." natural citations»
(`docs/plans/career-playbook/03-prompts-structure.md:245`). Оно просто не доехало до реализации.

### RC-5. Промпт прямо требует выдумывать конкретику

Во всех шести групповых промптах повторена строка: «For an illustrative name or value in narrative
prose, use a realistic invented example and mark it as an example»
(`career-playbook-prompts.ts:305,345,385,425,468,514`).

Это компенсация детерминированного детектора плейсхолдеров (`placeholder-detection.ts`,
`final-assembler.ts:241-274`): запрет на `[Name]`/`{value}` вытолкнул модель в выдуманные
конкретные значения. Так в universal-документе появились оклад $120,000/$60,000 (`:500-506`) и
сценарий $50M incremental ARR (`:843`). Один дефект обменяли на другой.

### RC-6. В промптах нет текущей даты

Ни один промпт трека не передаёт дату генерации (проверено по всему каталогу
`stage-career-playbook/` и `career-playbook-prompts.ts`). Модель по умолчанию использует эпоху
своих обучающих данных — отсюда Gantt онбординга, жёстко привязанный к январю-марту **2025**
(`:393-425`), и «training records 2024-2025» (`:929-935`) в документе от августа 2026.

### RC-7. Spec-builder упирается в потолок 8000 токенов — и это одновременно latency и quality

Самая дорогая единичная поломка прогона.

- `maxTokens: 8_000` в коде (`spec-builder.ts:176`) и `max_tokens 8000` в конфиге фазы
  (`supabase/migrations/20260523073000_update_career_playbook_v4_pro_routing.sql`).
- В прогоне `deepseek-v4-pro` вернул **ровно 8000** output-токенов (`run-record.json:19`) —
  подпись обрезки. Обрезанный JSON не прошёл валидацию.
- Repair-путь жёстко понижает модель: `preferFallbackModel: true` (`spec-builder.ts:187-191`) →
  ушёл на `v4-flash`, потратил 4 попытки × ~300 с = **1 047 291 мс ≈ 17,5 минуты**.

Итог: **19 из 56 минут (33%)** прогона, и спека — фундамент всех 26 блоков — построена самой
слабой моделью в деградированном режиме, выдав всего 2700 токенов против 8000 у первой попытки.
Качество всех блоков наследует эту спеку.

### RC-8. PDF-рендерер самописный и покрывает подмножество Markdown

`renderMarkdownBody` (`services/career-playbook-pdf-template.ts:129-247`) знает только h1/h2/h3,
таблицы, списки `-`/`*` и code fences. Всё остальное падает в `<p>` как сырой текст.

Замерено в сгенерированном документе:

| Конструкция         | Вхождений | Что в PDF                                |
| ------------------- | --------: | ---------------------------------------- |
| `#### `             |         3 | печатается буквально                     |
| `---`               |         9 | печатается буквально                     |
| Нумерованные списки |  37 строк | распадаются в абзацы                     |
| `[текст](url)`      |  0 сейчас | **сломается, как только добавим цитаты** |
| Вложенные списки    |  0 сейчас | схлопнутся                               |

`renderInlineMarkdown` (`:68-73`) обрабатывает только `code`/`strong`/`em` — ссылки в `<a>` не
превращает. Это блокирует пункт про цитаты.

### RC-9. Печатный CSS ломает пагинацию

- `.playbook-block-heading { break-before: page }` (`:328`) — каждый из 26 блоков начинает новую
  страницу; в связке с `break-inside: avoid` на фигурах и таблицах (`:338,347`) даёт полностью
  пустые страницы 20, 34, 57.
- У `.mermaid-diagram svg` задан только `max-width`, `max-height` нет (`:363`) — диаграмма выше
  страницы режется (58-59).
- Нет `orphans`/`widows` — отсюда «хвост FMEA на четверть страницы 50».
- Шрифт `Inter, Arial, sans-serif` без символьного покрытия — 21 вхождение ✅/⚠️ вырождается в
  квадраты (страница 32).

### RC-10. Обложка одинаковая для всех ролей

`buildPromptVars` подставляет константу `DEFAULT_CARD_VISUAL_STYLE` без вариации по департаменту
или роли (`stages/stage-career-playbook/image-generation.ts:123-126`). Отсюда «generic blue
business growth scene» вместо B2B-sales-лидерства.

## Целевая архитектура

### 1. `RoleProfileSpec` v2 — канонический реестр чисел и утверждений

В `packages/shared-types/src/career-playbook.ts` (`CareerPlaybookRoleProfileSpecSchema:808`)
добавляются три поля:

```ts
metric_ledger: z.array(z.object({
  key: z.string().min(1),              // 'pipeline_coverage'
  label: z.string().min(1),            // 'Покрытие воронки'
  unit: z.string(),                    // 'x' | '%' | 'дней'
  target: z.string().min(1),           // '>=3x'
  green: z.string(), yellow: z.string(), red: z.string(),
  review_period: z.string(),           // 'квартал'
  provenance: z.enum(['company_source', 'user_answer', 'benchmark', 'assumption']),
  source_ref: z.string().nullable(),   // id из evidence_ledger
})).default([]),

evidence_ledger: z.array(z.object({
  id: z.string().min(1),               // 'S1'
  url: z.string().min(1),
  title: z.string().min(1),
  claim: z.string().min(1),            // конкретное утверждение, которое источник подтверждает
  retrieved_at: z.string().min(1),
})).default([]),

generated_on: z.string().min(1),       // ISO-дата, проставляется кодом
```

Ключевой принцип, который надо соблюсти при реализации: **`evidence_ledger` и `generated_on`
заполняются детерминированно кодом**, а не «моделью, которая перепишет URL». `evidence_ledger`
собирается прямо из результата `runCareerPlaybookWebResearch` в `spec-builder.ts` после парсинга
спеки; `generated_on` — из системного времени. LLM отвечает только за `metric_ledger` (и то с
детерминированной нормализацией: дубликаты `key` схлопываются, пустые `target` отбрасываются).

Это тот же приём, что уже применён для канонической раскладки блоков:
`normalizeRoleProfileSpecToCanonicalBlockTopics` (`nodes/spec-builder-canonical.ts`) — сначала
просим модель, потом детерминированно приводим к контракту. Переиспользовать этот паттерн, а не
изобретать новый.

### 2. Групповые промпты v2 — четыре новые обязательные переменные

Все шесть промптов `career_playbook_group_*` получают:

| Переменная            | Содержимое                                                                               | Закрывает |
| --------------------- | ---------------------------------------------------------------------------------------- | --------- |
| `metric_ledger_md`    | Реестр как markdown-таблица                                                              | RC-1      |
| `evidence_ledger_md`  | Список `[S1] URL — утверждение`                                                          | RC-4      |
| `generated_on`        | Дата генерации                                                                           | RC-6      |
| `prior_blocks_digest` | Сжатая выжимка уже принятых блоков: анти-цели, обещанные пороги, названные обязательства | RC-2      |

Новые правила в теле промптов (заменяют текущую формулировку про «realistic invented example»):

1. **Числа.** Любое число, присутствующее в `metric_ledger`, воспроизводится **дословно**, вместе
   с порогами светофора. Вводить новое число для метрики из реестра запрещено.
2. **Внешние утверждения.** Точная статистика о рынке, отрасли или ИИ допускается только со
   ссылкой `[S1]` на `evidence_ledger`. Нет источника — переписывается как явная гипотеза
   («ориентир, требует проверки»), без точного процента.
3. **Примеры.** Company-specific пример (оклад, ARR, бюджет, имя, инструмент) остаётся конкретным,
   но обязан нести единый маркер — `(пример — заменить)` / `(example — replace)`. Все такие
   значения попадают в чеклист внедрения block_26.
4. **Даты.** В планах и графиках только относительные обозначения (День 1-30, Неделя 2, Квартал 1).
   Абсолютный календарный год допускается только для `generated_on` в футере block_25.

`prior_blocks_digest` строится детерминированно новым хелпером в `group-generator.ts` из
`state.generatedBlocks` — это же чинит уже существующую, но не используемую передачу контекста.

### 3. Четыре новые детерминированные проверки

Добавляются в `nodes/cross-block-judge-checks.ts` рядом с существующими
`validateAntiGoalsMinimum` / `validateDecisionMatrixMinimum` / `validateFailureModesMinimum` и
подключаются в `runCareerPlaybookDeterministicChecks` (`cross-block-judge.ts:261-292`).

| Проверка                          | Логика                                                                                                                                | Ловит                                               |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `validateMetricLedgerConsistency` | Ищет метку метрики из реестра и число рядом с ней; расхождение с `target`/порогами → `critical`                                       | Конфликты 2×/3×, ±10%/±5%, 85/90/100%, 15/10/25/30% |
| `validateUnsourcedStatistics`     | Точный процент/множитель + маркер внешнего утверждения (`research shows`, `studies`, `benchmark`, `industry`) без `[Sn]` → `critical` | «90-95% точность», «28% response rate»              |
| `validateExampleMarking`          | Денежная сумма или именованное лицо/инструмент в universal-режиме без маркера примера → `critical`                                    | $120,000/$60,000, $50M ARR                          |
| `validateRelativeDates`           | Абсолютный год ≠ году `generated_on` вне футера → `critical`                                                                          | Gantt «январь-март 2025»                            |

Почему детерминированно, а не через LLM: это ровно те четыре класса, которые ревью нашло глазами,
они формализуемы, стоят ноль долларов и ноль секунд, и не зависят от того, какая модель
досталась судье в этот раз.

### 4. Таксономия судьи v2

В `CareerPlaybookJudgeIssueCategorySchema` и `isCareerPlaybookJudgeCriticalCategory`
(`packages/shared-types/src/career-playbook.ts`) добавляются три критичные категории:
`metric_conflict`, `unsourced_claim`, `stale_date`. Промпт судьи
(`career-playbook-prompts.ts:545-587`) описывает их так же строго, как пять существующих.

Формулировка `contradiction` расширяется: противоречие **другому блоку** (а не только спеке) —
критично. Это возвращает требование, которое было в исходной спецификации
(`03-prompts-structure.md:281` — «anti-goals из блока 2 не противоречат duties из блока 4») и
потерялось при переписывании таксономии.

Ограничение «`style` никогда не ведёт к регенерации» сохраняется — оно правильное и экономит цикл.

### 5. Обоснованность: чиним web-research

- `search_depth: 'basic'` → `'advanced'`, `max_results` 5 → 8, таймаут 5 с → 20 с с одной
  повторной попыткой (`rag/web-research.ts:36,137-140`).
- Пустой/отсутствующий `TAVILY_API_KEY` перестаёт быть тихим: пишется предупреждение в
  `qualityWarnings` playbook-а, а генерация переходит в режим «без внешней статистики» —
  `validateUnsourcedStatistics` тогда режет любую точную цифру.
- `evidence_ledger` собирается из результатов детерминированно (см. п.1).
- Раздел «Источники» добавляется в конец документа (block_25), ссылки `[S1]` кликабельны —
  это требует поддержки ссылок в PDF-рендерере, см. п.7.

### 6. Надёжность и бюджет: как укладываемся в 25 минут и $0.35

Разбор текущих 56 минут по `run-record.json` и целевые значения:

| Участок              |     Сейчас |        Цель | Как                                                                                                                                                   |
| -------------------- | ---------: | ----------: | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| specBuilder          |     19 мин |      ~2 мин | `max_tokens` 8000 → 16000 (код + миграция); при обрезке — повтор на **той же** модели с увеличенным лимитом вместо принудительного понижения до flash |
| Генераторы групп     |     19 мин |     ~14 мин | `timeout_ms` 300 000 → 120 000: три неудачные попытки стоят 6 минут вместо 20                                                                         |
| Судьи                |     13 мин |      ~6 мин | Детерминированные проверки снимают часть нагрузки; delta re-judge уже включён                                                                         |
| Регенерации (13 шт.) |      7 мин |      ~3 мин | Реестр метрик убирает основную массу флагов `contradiction`/`invented_number`                                                                         |
| **Итого**            | **58 мин** | **~25 мин** |                                                                                                                                                       |

Стоимость: новые переменные добавляют примерно 1,5-2 тыс. входных токенов на группу — это порядка
$0.01-0.02 сверх текущих $0.123. Основной резерв бюджета остаётся на возможный проход вычитки
(см. «Отложено»).

Отдельно: в чек стоимости добавляются записи о **неуспешных и оборванных по таймауту** попытках со
стоимостью `unknown` — сейчас их в `costBreakdown` нет вообще, и приложение не может доказать,
сколько провайдер выставит за прерванные вызовы.

### 7. PDF: заменить самописный рендерер
