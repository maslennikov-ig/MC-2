# Summary

## Diagnosis

Dev document indexing does **not** fail because `course_embeddings` is missing, because an alias is wrong, or because the indexing code uses the wrong collection name.

It fails because the Dev runtime is configured with a **QDRANT_URL that does not serve a live Qdrant API at all**:

- Dev worker and API both use `QDRANT_URL=https://b66349de-ad5f-4d43-aa6e-8a2aab53542a.eu-central-1-0.aws.cloud.qdrant.io:6333`
- From inside `megacampus-worker-dev`, the official `@qdrant/js-client-rest` client returns:
  - `message: "Not Found"`
  - `actual.status: 404`
  - `actual.data: "404 page not found\n"`
- The same endpoint returns `404 page not found` even for `getCollections()` / `GET /collections`

Because `GET /collections` itself 404s, the failure is **upstream of any collection-specific operation**. That rules out:

- missing `course_embeddings` collection as the primary cause
- wrong alias
- wrong collection naming in application code
- deleted vectors within an otherwise healthy collection

The exact root cause is therefore:

**Dev `.env.dev` points to a stale/invalid/non-serving Qdrant Cloud endpoint (very likely a deleted or no-longer-live cluster URL), so every Qdrant API call hits a generic `404 page not found` before collection lookup even begins.**

## Confidence

High (`0.96`).

## Distinction: root cause vs application bug

### Actual root cause of `Not Found`

Invalid Dev Qdrant base endpoint (`QDRANT_URL`), not a collection/alias problem.

### Separate application bug

The Stage 2 orchestration path misreports the failed upload as success in logs:

- `uploadChunksToQdrant()` catches the Qdrant exception, marks the document failed in `file_catalog`, and returns `success: false`
- `executeQdrantUpload()` does not validate `uploadResult.success`
- `orchestrator-phase-helpers.ts` then logs `Vectors uploaded to Qdrant` unconditionally

So there are two problems:

1. **Infra/config root cause**: bad Qdrant endpoint
2. **Application observability/handling bug**: failed upload is logged/treated as uploaded in the Stage 2 path

- the JS client surfaces typed HTTP errors via `getActualType()`
- upsert/search/getCollection all use the configured base URL directly

That matches the runtime reproduction below: `Not Found` is the client wrapper around HTTP 404 from the server.

This means the application is consistently targeting `course_embeddings`; there is no local naming mismatch to explain the 404.

### 3. Dev runtime env: worker and API use the same Qdrant endpoint

From server/container inspection:

- `/opt/megacampus/.env.dev` contains

- `megacampus-worker-dev` env contains the same value
- `megacampus-api-dev` env contains the same value

So the failing worker is not using a different runtime URL than the API.

### 4. Runtime reproduction inside the real Dev worker

Inside `megacampus-worker-dev`, using the official JS client with the live env:

```json
{
  "message": "Not Found",
  "actual": {
    "status": 404,
    "data": "404 page not found\n"
  }
}
```

This happened for:

- `client.getCollections()`
- `client.getCollection('course_embeddings')`

If `getCollections()` itself 404s, the endpoint is not exposing Qdrant collections API at all. This is the strongest evidence that the base URL is wrong/stale/non-serving.

### 5. Direct HTTP check against the configured URL

Direct `curl` to the configured endpoint returned:

```text
HTTP/2 404
content-type: text/plain; charset=utf-8

404 page not found
```

This happened for:

- `GET $QDRANT_URL`
- `GET $QDRANT_URL/collections`
- `GET ${QDRANT_URL%:6333}/collections`
- `POST $QDRANT_URL/collections/course_embeddings/points/count`

So the problem is not:

- bad auth header only
- bad collection name only
- alias only
- port-only mistake

The configured host/path combination is simply not serving the expected Qdrant REST API.

### 7. Why Stage 6 later saw `ragChunksCount=0`

Relevant code:

- `packages/course-gen-platform/src/shared/rag/document-availability.ts:57-63`
- `packages/course-gen-platform/src/stages/stage6-lesson-content/rag/retriever.ts:46-56`

Stage 6 first checks Supabase for at least one document with `vector_status='indexed'`. Since the failed Stage 2 upload left the document at `vector_status='failed'`, RAG retrieval is skipped, so later stages naturally run with zero indexed documents / zero RAG chunks.

That is a downstream consequence of the Qdrant endpoint failure, not a second independent root cause.

### 8. Separate application bug in failure handling

Relevant code:

- `packages/course-gen-platform/src/shared/qdrant/upload.ts:277-320`
- `packages/course-gen-platform/src/stages/stage2-document-processing/orchestrator-phase-helpers.ts:239-249`

The failure path returns an `UploadResult` with zero uploaded points instead of throwing. The caller then logs `Vectors uploaded to Qdrant` unconditionally.

This matches the server log:

- `7184` upload failed
- `7186` document marked failed
- `7188-7189` still logs `Vectors uploaded to Qdrant`

That bug makes debugging noisier, but it is **not** the reason for the original 404.

## Proposed remediation

1. Replace Dev `QDRANT_URL` in `/opt/megacampus/.env.dev` with a live Qdrant API endpoint for the intended Dev cluster.
2. Verify the new endpoint before requeueing work:
   - `client.getCollections()` must return `200`
   - `client.getCollection('course_embeddings')` must return `200`, or create the collection first
3. If the live cluster has no `course_embeddings`, run the repo’s collection creation flow against the corrected endpoint.
4. Requeue/reprocess failed Dev documents for the affected course after the endpoint is fixed.
5. Follow-up code fix: make Stage 2 fail hard or at least branch on `uploadResult.success === false` instead of logging upload success unconditionally.
